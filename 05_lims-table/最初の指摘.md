### 不整合・矛盾

**1. 「静的表示の爆速化」とD1の関係が曖昧**  
Astroを静的ビルドにするのか、SSR（Cloudflare adapter）にするのかが書かれていません。D1はWorkers経由でしか触れないため、SSRまたはAPIルートが必要です。締め日は日々変わるので、「データ更新のたびに再ビルド」か「リクエスト時にD1を読む」かを決める必要があります。月数十件程度のデータなら、後者でもキャッシュ（`Cache-Control`）を効かせれば十分高速です。

**2. セットリストのデータモデルが機能要件を満たせない**  
「`songs` / `setlists` テーブル」と1つの見出しにまとめられていますが、中身は1テーブル分しかありません。このままだと次の問題が出ます。

- 「曲ごとの過去歌唱回数」の集計が、`song_title` の文字列一致に依存する（表記ゆれで壊れる）
- 同じ曲を複数回歌った場合、`songs` の1行に `stream_url` / `timestamp` が1つしか持てない

`songs`（曲マスタ）、`streams`（配信：URL・日付・タイトル）、`setlist_entries`（配信ID・曲ID・タイムスタンプ・順序）の3テーブルに分けるのが妥当です。

**3. ディスコグラフィ用のテーブルがない**  
2.2でリリース曲・MV・カバー曲のカタログ化を掲げていますが、データ構造案に対応するテーブルがありません。オリジナル曲/カバー曲の区別、リリース日、リンク先（複数）の持ち方が未定義です。

**4. Cloudflare Pages / Workers の表記が混在**  
現在CloudflareはWorkers（Static Assets）への統合を推奨する方向です。Pagesでの新規構築を前提にするなら、最新状況を確認してから確定したほうが安全です。Cron TriggersはPages単体では使えず、別Workerが必要な点も明記が必要です。

### 不足している仕様

**5. データ入力フローが未確定**  
「Notion API または簡易管理画面」と二択のままです。Notion APIを使うならD1との二重管理（同期処理）が発生します。簡易管理画面なら認証（Cloudflare Accessなど）が必要です。最小構成としては「D1に直接入れる管理画面＋Cloudflare Access」か、「Notionを唯一のソースにしてCronでD1へ同期」のどちらかに決めたほうがよいです。

**6. 日時・タイムゾーンの扱い**  
`deadline_at` が `DATETIME` ですが、SQLiteには専用の日付型がなく、TEXT（ISO 8601）で保存することになります。JST固定で保存するのかUTCなのか、「あと〇日」の計算基準（当日23:59締切の扱いなど）を決めておかないと、カウントダウンが1日ずれます。海外ファンを想定するかも含め、表示は「JST固定」と明記するのがおすすめです。

**7. `deadlines` テーブルの項目不足**

- 開始日時（受付開始）がない。「受付中/受付前/終了」の状態表示ができない
- 締め切りの更新・延長・中止の扱い（`status` や `updated_at`）がない
- 情報の出典URL（公式告知ポスト等）がない。非公式サイトで誤情報を出すリスクが高いため、`source_url` と最終確認日があると信頼性と権利配慮の両面で有効です
- カテゴリ `goods | ticket | voice | event` が、2.1のタグ表記（「ボイス・コンテンツ」等）と対応づけられていない（表示ラベルのマッピング定義が必要）

**8. マイリストの `localStorage` 設計**  
キー名・保存形式が未定義です（免責用は `nurojunk_disclaimer_accepted` と明記されている）。次の点を決めておくと後で困りません。

- 保存するのはアイテムID配列でよいか
- 終了済みアイテムのIDを掃除するか
- 端末間で同期されない旨のUI上の注記
- SSR時にlocalStorageを読めないため、ハイドレーション時のちらつき対策（React Islandで `client:only` にするなど）

**9. 免責モーダルのSEO・アクセシビリティ**  
初回モーダルで全画面を覆うと、JS無効環境やクローラーに対して本文が見えにくくなる場合があります。フォーカストラップ、キーボード操作、同意前のコンテンツの扱い、また「同意しない」場合の挙動（外部へ戻す等）が未定義です。免責文の本文案も別途必要です。

**10. X連携まわりの未定義事項**

- 通知先（Discord/Slack/LINE）を1つに決めていない。LINE Notifyは2025年に終了しているため候補から外すべきです
- 文面のテンプレート、文字数上限（日本語は全角140字換算ではなく重み付けカウント）への対応
- 「重要度の高いもの」の判定は `is_priority` で手動指定のため、運営者が付け忘れた場合のフォールバックがない
- 「毎朝」の時刻、締め日が0件の日は通知しないのか

**11. 権利・ガイドライン面**

- 対象VSingerやその運営が公表している二次創作・ファンサイトのガイドラインの確認が前提になりますが、仕様に確認事項として入っていません。サイト名に固有名詞を使う点も含め、事前確認の記載があるとよいです
- 歌配信のセットリストは、原曲の楽曲名・アーティスト名の掲載のみで歌詞は載せない旨を明文化しておくと安心です
- YouTube埋め込みやタイムスタンプ付きリンクの利用規約上の扱い
- プライバシーポリシー（localStorage利用、Cloudflareのアクセスログ、アクセス解析を入れるか否か）

**12. 非機能要件が皆無**

- 運営者が更新できなくなった場合の方針（サイトの閉じ方・アーカイブ化）
- バックアップ（D1のエクスポート手順）
- 無料枠の上限（D1の読み取り行数、Workersのリクエスト数）の見積もり。特にセットリスト検索で全文検索をLIKEで行うとrow読み取りが膨らみやすいです
- 検索の方式（SQLite FTS5を使うか、データ量が少ないならクライアント側検索か）が未定

### 軽微な点

- 技術スタック欄の「ポートフォリオ開発の知見をそのまま活用可能」は仕様書に残す内容としては選定理由になっておらず、削除するか技術的理由に置き換えたほうがよいです
- 月間カレンダー表示の実装方針（自前実装かライブラリか）が未定
- フェーズ3の「Worker / GAS」は、どちらにするか決めておかないとフェーズ2のデータ構造設計に影響します（GASならD1に直接アクセスできず、API経由が必要）
- フェーズ1に、サイト名・ドメイン取得・`robots.txt`・OGP方針などの公開準備が入っていません
