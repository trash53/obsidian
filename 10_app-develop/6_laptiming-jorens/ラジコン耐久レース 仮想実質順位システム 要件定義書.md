# ラジコン耐久レース 仮想実質順位システム 要件定義書

第1.0版（ドラフト）／作成日：2026年11月4日

## 1. 目的と範囲

### 1.1 目的

ラジコン耐久レースでは、ピットイン（バッテリー交換等）のタイミング差により、コース上の順位（実順位）がチームの実質的な位置関係を表さない。本システムは、未消化のピット分のロス時間を加味した「仮想順位」と「仮想タイム差」をリアルタイムに算出・表示し、ピットインのタイミング判断を支援する。

### 1.2 対象

- 対象レース：6台程度、1周約20秒、時間制の耐久レース
- 計測システム：MYLAPS（RC4＋集計ソフト）。ライブ配信はインターネット経由で取得する想定
- 利用者：チームの戦略担当（閲覧）、ピットクルー（ピット回数の入力）

### 1.3 範囲外

- 他チームの走行への干渉、公式結果の代替（本システムの順位は参考情報であり、公式順位ではない）
- 周回数の手入力による運用（20秒/周では現実的でないため廃止）

## 2. 用語

| 用語 | 意味 |
| --- | --- |
| 実順位 | 公式ルールに沿った現時点の順位。周回数が多い方が上位、同一周回なら、その周の通過時刻が早い方が上位 |
| 仮想順位 | 未消化ピットのロスを加算して比較した順位 |
| 想定ピット回数 | ルールでは定められていない。バッテリーの持ち（約30分）から見積もった総ピット回数の想定値（設定値。初期値8、7〜8の範囲でチームごとに変更可） |
| 想定ピットロス時間 | 1回のピットインで失う標準時間（設定値。初期値は40秒、練習走行で実測して決める） |
| 通過イベント | あるチームが計測地点を通過した記録（チームID、周回番号、通過時刻） |
| 基準周回 | 全チームが通過済みの最新の周回番号。仮想順位の比較に用いる |

## 3. システム構成

```
[取得アダプタ] → 通過イベント → [履歴保存] → [計算エンジン] → [画面]
                                              ↑
                                [ピット回数入力]・[設定値]
```

取得アダプタは、計測システム側のデータ形式の違いを吸収する部品である。計算エンジンと画面は、アダプタの出力（通過イベント）だけを入力とする。これにより、通信形式が未確定の段階でも、アダプタ以外を開発できる。

## 4. 機能要件

### 4.1 データ取得（取得アダプタ）

1. 計測システムのライブ配信から、各チームの通過イベントを自動取得する。周回数・通過時刻の手入力は行わない。
2. 内部の共通形式は次のとおりとする。
   - チームID、チーム名、周回番号、通過時刻（レース開始からの経過秒）、取得時刻
3. 取得元の時刻基準がレース開始からの経過時間でない場合、アダプタが次のいずれかで変換する。
   - 取得元の起点（スタートの合図）に合わせる
   - 手動の「レーススタート」操作の時刻を基準にする（予備機能として備える）
4. 取得間隔は10〜30秒に1回を基本とし、設定で変更できる。
5. 各周の通過履歴（ラップチャート相当）を取得する。現在の周回数と総時間のみしか取れない場合は、更新のたびに通過イベントを自前で組み立てる。
6. 動作確認用に、過去レースのデータやダミーデータを流す仮のアダプタを用意する。

### 4.2 履歴の保存と復旧

1. 取得した通過イベントは、アプリ側に追記方式で保存する（SQLiteまたはJSON）。取得元が古いデータを破棄しても、自前の履歴が残る。
2. 保存は「チームID＋周回番号」をキーとして上書きする。主催者によるラップ修正や、重複受信にも整合が取れるようにする。
3. 周回番号の抜けを検出したら、画面に警告を出す。
4. 取得結果と自前の履歴が食い違った場合は、取得元を優先して更新し、変更を記録する。
5. アプリやPCが落ちた場合は、保存済みの履歴から復旧できる。
6. 保存した履歴は、レース後の検証と過去データによる試験に使える。

### 4.3 順位計算

#### 4.3.1 実順位

周回数が多いチームを上位とする。周回数が同じ場合は、その周回の通過時刻が早いチームを上位とする。

#### 4.3.2 仮想順位（同一周回基準方式）

先頭の周回数に対する比較では、周回数が多いチームが総時間で不利に見えてしまう。これを避けるため、全チームが通過済みの周回（基準周回K）で比較する。

```
仮想タイム_i ＝ チームiのK周目通過時刻
              ＋ max(0, 想定ピット回数_i − 消化ピット回数_i) × 想定ピットロス時間
```

- 仮想タイムが小さいチームを上位とする。
- 想定を超えてピットインしたチームは、残りピット回数を0とし、ロスを負にしない。ピット回数はルール上の義務ではないため、チームごとに想定回数を変えると、その差×ピットロス時間（40秒×差）が順位に反映される。
- 基準周回は最も遅いチームの周回に依存するため、仮想順位は最大で1周分（約20秒）遅れて更新される。この遅れは許容する。
- 仮想タイム差は、仮想先頭との差と、前後車との差の両方を算出する。

#### 4.3.3 レース終了

1. レース時間が経過したら、各車はその後の最初の計測地点通過をもってゴールとする。
2. ゴールが確定した車は、周回数と通過時刻で最終順位を確定する。全車確定後は、確定順位を表示する。
3. 時間切れ後の最初の通過の扱いが会場の集計ソフトと異なる場合は、集計ソフトの結果を優先する（未確定事項参照）。

### 4.4 ピット回数の入力

1. ピット回数は手動でカウントする。クラッシュや停止走行による誤判定を防ぐため、自動判定は行わない。
2. 各チームに「＋1ピット」ボタンと「−1（修正）」ボタンを設ける。
3. リーダーボードとは別画面（スマホ向け）とし、押し間違いを減らすため、誤操作を防ぐ確認や取り消しを設ける。
4. 複数の端末から入力しても、同じ値が共有される。
5. 入力履歴（時刻、操作）を保存する。

### 4.5 設定値

想定ピット回数（初期値8、チームごとに変更可）、想定ピットロス時間（初期値40秒）、レース時間、取得間隔、自チームの指定を、画面から変更できる。想定ピットロス時間は、練習走行で実測して決める。

### 4.6 画面表示

#### 4.6.1 リーダーボード（メイン画面、1行1車）

| 列 | 内容 |
| --- | --- |
| 実順位 | 4.3.1の順位 |
| 仮想順位 | 4.3.2の順位。実順位との差を▲▼で表示 |
| チーム名 | 自チームはハイライト |
| 周回数 | 現在の周回数 |
| 直近ラップ | 直近1周のラップタイム |
| 直近5周平均 | ペース把握用。周回数は設定で変更可 |
| ベストラップ | 参考表示 |
| ピット | 消化数／想定数（未消化が分かるように） |
| 仮想先頭差 | 仮想タイムでの先頭との差（秒） |
| 前後車差 | 仮想順位で前後の車との差（秒） |

#### 4.6.2 補助表示

- レースの残り時間（または経過時間）
- データの最終更新時刻と、古さの警告
- 周回の抜けなどの警告

#### 4.6.3 順位変動チャート

- 周回ごとの実順位の推移を折れ線で表示する（演出要素）。
- 仮想順位への切り替え、または重ね表示ができるようにする。

## 5. 非機能要件

1. 利用環境：PC、スマホ、タブレットのブラウザで動作する。
2. 取得から画面への反映までの遅れ：取得間隔を含めて30秒以内を目標とする。
3. 通信：テザリング接続を想定する。推定データ通信量は10〜30MB/時間。従量制課金接続の設定をONにする。
4. 通信が途切れた場合：直前の値で計算を継続し、「データが古い」ことを画面に表示する。復旧後は自動で再取得する。
5. 信頼性：電源断や再起動から、保存済みの履歴で復旧できる。
6. 規模：6台程度。20秒/周で4時間規模のレースを処理できる。
7. 利用上の注意：本システムの順位は参考情報であり、公式結果ではない。ライブ配信データの利用は、主催者の了承を得て行う。

## 6. 前提条件と未確定事項

練習走行日などに、次の項目を確認する。いずれも、確認結果によって影響を受けるのは主に取得アダプタである。

| No. | 確認事項 | 影響 |
| --- | --- | --- |
| 1 | 会場の集計ソフトの種類（RCM等）と、Speedhiveへのライブ配信の有無 | 取得方式 |
| 2 | ライブ画面の通過時刻の基準（スタートからの経過か、時刻そのものか） | アダプタでの時刻変換、手動スタートの要否 |
| 3 | 画面で見られるラップチャートのデータを、プログラムで取得できるか | 取得方式 |
| 4 | 取得できる過去データの範囲（レース全体か直近のみか） | 保存の仕組みで吸収。計算部分への影響は小さい |
| 5 | 配信の受信遅延 | 通過時刻の誤差、遅延設定 |
| 6 | スタートのブザーが時間計測の起点か、最初の通過が起点か | 時刻基準、終了判定 |
| 7 | 時間切れ後の最初の通過をゴールとする扱いの確認 | 終了判定 |
| 8 | 想定ピット回数（7か8か）と想定ピットロス時間（40秒前後）の妥当性。練習走行で実測して確定する | 設定値 |
| 9 | 主催者による、ライブ配信データの利用の了承 | 運用可否 |

## 7. 開発フェーズ

1. **フェーズ1：計算エンジンと仮のアダプタ。** 過去データまたはダミーデータで、実順位、仮想順位、終了判定、履歴保存を作る。
2. **フェーズ2：画面とピット入力。** リーダーボード、順位変動チャート、ピット入力画面を作り、ダミーデータで通しの動作確認を行う。
3. **フェーズ3：実データ取得。** 練習走行日に未確定事項を確認し、本物のアダプタを作って、実運用に投入する。

## 8. 技術スタックと構成

実装言語はPython、会場のPC1台でサーバーを動かし、各端末のブラウザから利用する。クラウドを使わないので、会場の通信が不安定でも動作を継続できる。

### 8.1 技術スタック

| 部分 | 採用技術 | 理由 |
| --- | --- | --- |
| 取得アダプタ | Python（httpx。画面描画が必要な場合は Playwright） | `speedhive-tools` もPythonで、スクレイピングに向く |
| 計算エンジン | Python（純関数）＋pytest | 過去データで自動テストでき、フェーズ1の検証に使える |
| 履歴保存 | SQLite | 追記と上書きが簡単で、再起動後に復旧できる |
| サーバー | FastAPI（画面の配信も同一プロセス） | 軽量で、更新をブラウザへ送れる |
| リアルタイム更新 | Server-Sent Events（SSE） | 一方向の更新なので、WebSocketより単純 |
| 画面 | HTML＋JavaScript（必要なら Preact）＋Chart.js | 6台の表示に重いフレームワークは不要。順位チャートは折れ線（縦軸反転） |
| ピット入力 | 同一サーバーの別ページ（スマホ向け） | 全端末で値が共有される。ホーム画面に追加してアプリのように使える |

### 8.2 運用構成

1. PC1台でサーバーを起動する。
2. リーダーボードはPCまたはタブレットのブラウザで表示する。
3. ピット入力は各スマホのブラウザで開く。
4. PCのネット接続はUSBテザリングとし、端末間はPC側のWi-Fiホットスポットでつなぐ。事前に動作を確認する。

### 8.3 プロジェクト構成

```
virtual-standings/
  core/
    models.py      # 通過イベント、設定値のデータ型
    standings.py   # 実順位・仮想順位・終了判定（純関数）
    stats.py       # 直近ラップ、5周平均、ベスト
  adapters/
    base.py        # アダプタの約束（通過イベントを返す）
    dummy.py       # ダミーデータ生成（6台・20秒/周・ピット含む）
    live.py        # 本物のアダプタ（練習走行日に作成）
  storage/
    db.py          # SQLite（追記・上書き・復旧）
  server/
    app.py         # FastAPI（SSE、ピット入力API）
    static/        # リーダーボード、ピット入力ページ
  tests/           # 計算ロジックのテスト
```

### 8.4 採用しないもの

- React、Next.js などの本格的なフロント構成：6台の表示には過剰
- Firebase などのクラウド前提の構成：会場の通信状況に左右される

### 8.5 将来の拡張

複数人が別の場所から見たい場合は、クラウド中継を後から追加できる。初期版には含めない。
