# Obsidian Hub システム仕様書 v2

作成日: 2026-10-31 / 対象: iPhone SE（第3世代）+ Chrome / 状態: モック確認済み・実装前

## 1. 概要と目的

スマホからObsidian（GitHubリポジトリ管理）へ、予定・ログ・Webクリップを素早く書き込む軽量PWA。さらに、Gemini APIを使ったチャットUIを内蔵し、**Geminiとの会話や調べ物で得た知見を、要約してデイリーノートに蓄積し、あとで見返せるようにする**ことを主目的とする。

## 2. 前提・確定事項

- 利用端末: iPhone SE 3 / Chrome（iOSのため描画エンジンはWebKit）。ホーム画面に追加してPWAとして使う。
- 認証: Cloudflare Zero Trust（Access）のメールOTP。
- 日付・時刻はすべてJST（Asia/Tokyo）で扱う。Cron自体はUTCで動くため、日付決定時にJSTへ変換する。
- 親指ファーストと他の仕様が競合する場合は、親指ファーストを優先する。
- フォルダ: `30_calendar/daily-note/`（日次）、`30_calendar/events/`（予定）。スペルは calendar が正。
- 予定ファイル名: `YYYY-MM-DD_タイトル.md`。
- Obsidianプラグイン Full Calendar を利用中。

## 3. システム構成

- **フロント**: PWA（HTML/CSS/JS）。Cloudflare Workers (Static Assets) で配信。Tailwind CDNは使わず、ビルド済みの静的CSSまたは素のCSSにする。
- **バックエンド**: Cloudflare Workers。GitHub API中継、Gemini API呼び出し、認証情報の秘匿を担う。
- **DB**: Cloudflare D1（チャット、メッセージ、TODO、処理済みID）。
- **定期処理**: Cron Triggers（5分ごと）。30分無更新のチャットを要約する。
- **保存先**: GitHubリポジトリ（Markdown）。ブランチは `main` 固定。
- **Secrets**: GitHub PAT（fine-grained、対象リポジトリ1つ、Contents: Read and writeのみ）、Gemini APIキー。

## 4. 機能仕様

### 4.1 書き込み共通（追記方式）

- 送信時に、対象ファイルを**最新で再取得してから追記**する。画面でshaを保持して上書きする方式は採用しない。
- GitHubが409/422を返した場合は、再取得→再追記を最大3回繰り返す。それでも失敗したらoutboxに戻して後で再送する。
- 画面上のファイル状態表示（取得済み・最終更新時刻）は、確認用の表示のみ。
- GETで得たbase64はTextDecoderでUTF-8に復元し、書き込み時はTextEncoderでbase64化する（日本語の文字化け防止）。
- 存在しないファイル（404）はテンプレートから新規作成する。
- コミットメッセージ: `hub: log 2026-10-31 15:20` / `hub: event 2026-11-02_デザインレビュー` / `hub: clip 2026-10-31 15:20` / `hub: chat-summary 2026-10-31 15:50`。

### 4.2 カレンダー（予定）

- 入力項目: タイトル、日付、種類（時間指定 / 終日）。時間指定のときだけ開始・終了の時刻欄を表示する。
- 1予定につき1ファイル。`30_calendar/events/YYYY-MM-DD_タイトル.md` を新規作成する。**追記はしない**。
- 同名ファイルがある場合は `_2`, `_3` を付ける。
- ファイル名から次の文字を除去する: `/ \ : * ? " < > |`。先頭末尾の空白も除く。長さは80文字まで。
- frontmatter（Full Calendar形式）:

```
---
title: デザインレビュー
allDay: false
date: 2026-11-02
startTime: 15:00
endTime: 16:00
---
```

終日の場合は `allDay: true` とし、startTime / endTime を省く。

- カレンダータブを下にスクロールすると、**今日と明日の予定リスト**を表示する（終日を先頭、以降は時刻順）。
- 取得方法: eventsフォルダの一覧から、ファイル名が今日・明日の日付で始まるものを取り、frontmatterを読んで表示する。

### 4.3 デイリーノート

- 保存先: `30_calendar/daily-note/YYYY-MM-DD.md`（ファイル名が日付のため、本文に日付見出しは置かない）。
- 追記先は見出しで決める。見出しがなければ、ファイル末尾に作る。
  - `## Log`: ログ。形式 `- HH:mm 本文`（案）。複数行は2行目以降をインデントして続ける。
  - `## Web Clips`: Webクリップ。形式は下記。
  - `## AI Chats`: Gemini要約（4.5参照）。

```
- [ページタイトル](URL)
  - 補足メモ
```

- ファイルがない場合の新規作成テンプレートは、**ユーザーの既存デイリーノートのテンプレートに合わせる**（未提供のため未決事項に記載）。
- Webクリップの入力経路（iPhoneではWeb Share Targetが使えないため）:
  1. アプリ内の「クリップボードから貼り付け」ボタン。共有カード（カードC）にタイトル・URL・メモを表示し、確認して追記する。
  2. iOSの「ショートカット」アプリの共有シート項目から、`POST /api/entries`（type: share）を直接呼ぶ。トークンの扱いは9章を参照。
  3. 貼り付けテキストにURLが混在している場合は、URLを抽出して分離する。

### 4.4 Geminiチャット

- Gemini API経由のチャットUI。**複数チャットの同時進行**に対応する。
- チャット一覧には、チャットごとに「要約まで あと◯分」または「要約済み」を表示する。
- 通信が必須のため、**オフライン時は送信不可**（入力欄は無効化し、理由を表示する）。
- Geminiに送る文脈は「途中要約 + 直近N往復」とする（Nの初期値は6、設定で変更可能）。
- 新しいチャットのタイトルは、最初のやり取りからGeminiに自動生成させる。

### 4.5 自動要約（30分ルール）

- **区切り**: チャットごとに、最後のメッセージから30分経過したら要約する。
- **Cron**: 5分ごとに実行し、`last_message_at` から30分以上経過し、未要約メッセージがあるチャットを検出する。誤差は最大5分程度。
- **段階的要約（トークン節約）**: 未要約メッセージが閾値（初期値: 20件、または約6,000トークン）を超えたら、古い部分を `rolling_summary` に畳み込む。多少の精度低下より、トークンの余裕を優先する。最終要約は「途中要約 + 残りメッセージ」から作る。
- **書き込み先の日**:
  - 最初の要約: そのチャットのセッション開始日（JST）のデイリーノート。日をまたいでも開始日に書く。
  - 要約後に同じチャットが再開された場合: 再開後の部分を新しい要約とし、**再開した日**のデイリーノートに、タイトルに「（続き）」を付けて追記する。
- **全文ログ**: Obsidianには保存しない。要約が成功したら、D1上のメッセージ全文を削除する（再要約の保険として一定期間残すかは未決事項）。
- **要約フォーマット**:

```
## AI Chats
### 15:20 Cloudflare Workersのcron設計
**要点**
- D1を採用
- チャット単位で30分判定
**決定・TODO**
- 決定: D1を使う
- [ ] Cronのスケジュールを確認 📅 2026-11-05
```

- 要約が失敗した場合は、次のCronで再試行する（最大3回。超えたら状態を `failed` にして一覧に表示する）。

### 4.6 TODOとカレンダーの連携

- 要約時に、Geminiが決定事項とTODO（期限があれば期限も）を抽出する。
- 期限付きTODOはD1に `pending` で保存し、**チャットタブ上部の確認カード**に表示する。ユーザーが「登録」を押したものだけ、終日予定として events に作成する。「見送り」は予定を作らない。
- 誤抽出で予定が汚れるのを避けるため、**自動登録はしない**。
- 期限なしのTODOは、デイリーノートの `- [ ]` のみとする。
- Full Calendarのタスク形式（frontmatterの `completed: false`）の動作は、実装時にユーザーの環境で確認する。

### 4.7 オフライン対応

- 起動時にオフラインなら、取得を行う前にバナーで「オフラインです。入力は端末に保存され、接続後に自動で送信されます」と表示する。
- オフライン中も、予定・ログ・Webクリップの入力を受け付ける。IndexedDBの `outbox` に、クライアント生成のUUIDを付けて保存する。
- 再送タイミング: アプリ起動時、`online` イベント、送信中のリトライ。**iOSはBackground Syncが使えないため、アプリを閉じている間は送信されない**。
- リトライ間隔: 5秒 → 15秒 → 1分 → 5分。以降は次回起動時に再試行する。
- 未送信件数は、ヘッダーのバッジに常時表示する。
- 二重登録防止: WorkerはD1の `processed_ids` にUUIDを7日間記録し、同一IDは無視して `duplicate` を返す。
- iOSは、長期間使われないWebアプリのデータを削除することがある。未送信分は早めに同期する。

## 5. UI/UX仕様

### 5.1 構成

- 下部タブ: カレンダー / デイリー / チャット。
- 画面最下部に固定アクションバーを置く（タブの真上）。カレンダー・デイリーでは保存/追記ボタン、チャットの会話画面では入力欄と送信ボタン。safe-area（`env(safe-area-inset-bottom)`）に対応する。
- ヘッダー右に、接続状態と未送信件数のバッジ（タップでオフライン表示のデモ切替はモック専用。本実装では状態表示のみ）。
- ダークモードを基本とする（ライトにも追従可）。配色トークンはモックを踏襲する。

### 5.2 モック確認で出た修正点（本実装で対応）

1. **はみ出しの修正**: 日付・時刻の入力欄が、カードの右端からはみ出す。入力欄に `min-width: 0`、`max-width: 100%`、`-webkit-appearance: none` を指定し、横並びの子要素にも `min-width: 0` を付ける。
2. **改行の修正**: 「見送り」が2行に折れる。ボタンに `white-space: nowrap` と `flex: none` を指定し、テキスト側が縮むようにする（`min-width: 0`）。ボタンは「見送り」「登録」とも横幅を同じにそろえる。
3. **「＋新しいチャット」の固定**: チャット一覧をスクロールしても、「＋新しいチャット」ボタンを画面下部（タブの真上）に固定表示し続ける。一覧の末尾が隠れないよう、スクロール領域の下余白を確保する。会話画面では、同じ位置が入力欄に切り替わる。

### 5.3 画面別の内容

- **カレンダー**: 入力フォーム → 下スクロールで今日・明日の予定。保存先ファイル名をリアルタイム表示する。
- **デイリー**: ログ / Webクリップの切替。ログは `## Log` へ、クリップはカードCで確認して `## Web Clips` へ。今日の追記履歴を下に表示する。
- **チャット**: 上部にTODO確認カード、続いてチャット一覧、固定の「＋新しいチャット」。会話画面には、最後のメッセージからの経過時間と要約プレビューを表示する。

## 6. API仕様

すべてZero Trust配下で動作する。

- `GET /api/note?date=YYYY-MM-DD`: デイリーノートの内容と状態（存在有無、最終更新）を返す。
- `GET /api/events?from=YYYY-MM-DD&to=YYYY-MM-DD`: 期間内の予定一覧を返す。
- `POST /api/entries`: 予定・ログ・クリップの書き込み。

```
{ "id": "uuid", "type": "log",   "date": "2026-10-31", "data": { "time": "15:20", "text": "..." } }
{ "id": "uuid", "type": "event", "date": "2026-11-02", "data": { "title": "...", "allDay": false, "startTime": "15:00", "endTime": "16:00" } }
{ "id": "uuid", "type": "share", "date": "2026-10-31", "data": { "title": "...", "url": "...", "text": "..." } }
```

応答: `{ "status": "ok" | "duplicate" }`。

- `GET /api/chats`: チャット一覧（状態、残り時間）。
- `POST /api/chats`: 新規チャット作成。
- `GET /api/chats/:id`: 会話の取得。
- `POST /api/chats/:id/messages`: メッセージ送信。Gemini呼び出しと、D1への保存を行う。
- `GET /api/todos?status=pending`: 確認待ちTODO。
- `POST /api/todos/:id/approve` / `POST /api/todos/:id/dismiss`: 登録 / 見送り。
- 内部処理（画面からは呼ばない）: Cronによる要約と、デイリーノートへの追記。

## 7. データモデル（D1）

- `chats`: id, title, state（active / summarized / failed）, session\_start\_at, last\_message\_at, rolling\_summary, summarized\_upto\_message\_id, retry\_count。
- `messages`: id, chat\_id, role, content, created\_at。
- `todos`: id, chat\_id, text, due\_date, status（pending / approved / dismissed）。
- `processed_ids`: id, created\_at（7日を過ぎたら削除）。

## 8. PWA要件

- `manifest.json`: name, short\_name, start\_url, display: standalone, theme\_color, background\_color, アイコン（192/512、maskable）。
- Zero Trust配下のため、manifestの `<link>` に `crossorigin="use-credentials"` を付ける。
- Service Worker: アプリシェルのキャッシュのみ。APIレスポンスはキャッシュしない。
- iOSでは、PWAとブラウザでストレージ・ログイン状態が別になる。初回はPWA内でOTPログインを行う。Access のセッション期間は長め（例: 30日）に設定する。
- iOSに `share_target` は効かないため、manifestには記載しなくてよい。

## 9. セキュリティ

- Zero Trust（メールOTP）で、Worker全体（静的ファイルとAPI）を保護する。
- GitHub PATとGemini APIキーは、Worker Secretsにのみ保存する。クライアントには出さない。
- ショートカット（iOS）からの呼び出しにはブラウザのOTPセッションがないため、Access のサービストークンを使う方式を実装時に検討する（トークンはショートカット内に保存するため、取り扱いに注意）。
- チャット内容は機微な情報を含みうるため、Workerのログに本文を出力しない。

## 10. 実装順序（案）

1. Worker基盤 + GitHub書き込みコア（再取得→追記→リトライ、予定ファイル作成）。
2. PWAフロント（モックを実装化、5.2の修正を含む）、manifest、Service Worker。
3. オフラインoutbox（IndexedDB）と再送、`processed_ids`。
4. Geminiチャットと複数チャット管理（D1）。
5. Cron要約（段階的要約、デイリーノート追記）。
6. TODO抽出と確認カード、Full Calendar連携。
7. iOSショートカット連携（Webクリップ）。
