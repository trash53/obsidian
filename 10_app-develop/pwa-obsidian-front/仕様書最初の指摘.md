## レビュー結果：仕様書 × サンプルHTML

全体として方向性は明確ですが、仕様書の記述が未完成の箇所と、HTMLが仕様の大半を未実装（モック状態）の点が目立ちます。

### 1. 仕様書の不備（優先度高）

**記述の破損・未完成**

- 3.3の追記フォーマットが `- 要検討` で途切れており、コードブロックも閉じられていません。ログのフォーマット（時刻の有無、箇条書きの形式など）が決まっていません。
- 1. 概要の末尾に空行があり、何か書きかけの可能性があります。

**表記の揺れ・誤字**

- `30_calender/daily note` と `30_calendar/events` でスペルが不一致です（calender / calendar）。実際のフォルダ名に合わせて統一してください。`daily note` のスペースもパス処理で事故になりやすいので、実際のパスを確認してください。
- ファイル名規則 `YYYY-MM-DD[events title].md` は区切りが不明確です。`YYYY-MM-DD_タイトル.md` や `YYYY-MM-DD 会議名.md` のように具体例を入れてください。また、タイトルに `/` や `:` が含まれる場合のサニタイズ規則が必要です。
- ホスティングが「Cloudflare Worker」とされていますが、静的配信は Workers (Static Assets) か Pages かを明記してください。

**仕様の矛盾・曖昧さ**

- 3.2「予定を入れる当日と翌日のカレンダーを表示」とありますが、カードA〜Cのどこに表示するのかが4章にありません。
- 3.2「既にあれば追記」とありますが、eventsファイル内の追記位置・フォーマット（時刻、チェックボックス、frontmatterの有無）が未定義です。
- デイリーノートが存在しない場合の新規作成テンプレート（`## Log` や `## Web Clips` 見出しを含む）が未定義です。見出しが存在しない場合の挙動（末尾に作るのか）も必要です。
- 「予定」は日時指定が前提なのに、時刻入力欄の仕様が3.2にも5.1のペイロードにもありません。

### 2. 仕様書で欠けている重要項目

1. **認証・セキュリティ**：「認証情報を秘匿」とあるだけで、GitHub PAT をWorker Secretsに置く点や、Worker自体へのアクセス制御（Cloudflare Access、共有トークンなど）が書かれていません。これがないとURLを知る人は誰でも書き込めてしまいます。
2. **コンフリクト時の挙動**：shaが不一致（409/422）のときにどうするか（再取得して再マージ、ユーザーに通知、追記なので自動リトライなど）が未定義です。今回の用途は「追記」なので、再取得して再追記する方式が現実的です。
3. **PWA要件**：`manifest.json`、Service Worker、アイコンの記載がありません。
4. **Web Share Targetの詳細**：manifestの `share_target` 設定（`method`、`action`、`params`）が未記載です。なお、**Web Share Target APIはAndroid ChromeでPWAをインストールした場合に動作**し、iOS Safariでは非対応です。対応環境を明記してください。
5. **エラー処理・オフライン時**：通信失敗時の再送キューや、送信中の状態表示がありません。
6. **文字コード・改行・タイムゾーン**：日付はJST前提であることを明記してください（後述のHTMLの問題と関連）。
7. **GitHub API**：ファイルが大きい場合や、5.1のGETで `sha` と `content`（base64のUTF-8デコード）を扱う注意点、リポジトリのブランチ指定、コミットメッセージ規則が未記載です。
8. **ペイロード**：`type` が `'share'` のとき `title` / `url` / `text` をどう渡すかが定義されていません（`content` 一本では分離できません）。

### 3. サンプルHTMLの不足・問題点

**仕様との乖離（未実装）**

- **API通信が未実装**：`submitToGitHub()` は `alert` のみです。ここは検証用のダミーで、実際の fetch 呼び出しが必要です。しかもメッセージが「安全に書き込みました」と断言しており、誤解を招きます。
- **セーフティPull（sha取得）が未実装**：カードAの「ターゲットファイル状態（shaインジケータ）」がありません。日付変更時の `GET /api/note` も呼ばれません。
- **カードCが存在しない**：共有データの自動プレビュー・確認欄がなく、共有は常に「デイリー」モードのフォームに流し込むだけです。仕様の `share` タイプ（Web Clips）とも結びついていません。
- **share型の区別がない**：現状 `currentMode` は `calendar` / `daily` の2値のみで、Web Clips向けの `share` 出力がありません。
- **時刻入力がない**：カレンダー登録なのに日付のみで、時刻や終了時刻の欄がありません（タイトルに自由記述する前提になっています）。
- **「当日と翌日のカレンダー表示」がない**。
- **URLクエリ受け取りがない**：実際の Share Target は `?title=...&text=...&url=...` で遷移してくるため、`URLSearchParams` で読み取る処理が必要です。`simulateShare()` はボタン押下のみです。
- **PWA関連が一切ない**：manifest、Service Worker、`<link rel="manifest">`、theme-color が未設定です。

**実装上のバグ・懸念**

- **日付がUTCになる**：`new Date().toISOString().split('T')[0]` はUTC基準のため、日本時間の0〜9時に前日の日付が入ります。ローカル日付で生成してください。
- **Tailwind CDN**（`cdn.tailwindcss.com`）は開発用で、本番非推奨です。ビルドして静的CSSにするのが望ましく、Service Workerでのオフラインキャッシュも難しくなります。
- **親指ファースト設計と不一致**：仕様では「主要アクションを画面下部に配置」ですが、送信ボタンはカード内で中央付近にあります。`fixed bottom-0` のアクションバーにして、safe-area（`env(safe-area-inset-bottom)`）対応も必要です。
- **`sticky` ヘッダーの `bg-surface/80`** は問題ありませんが、背景色トークン `surface` が `bg-surface/80` でも動くのは Tailwind 3系のCDNだからで、バージョン固定がないと挙動が変わり得ます。
- **アクセシビリティ**：モード切替ボタンに `aria-pressed` / `role="tab"` がなく、`input` の `label` は `for` 属性でひも付いていません。
- **二重送信防止・送信中表示がない**。`alert` はモバイルPWAでは体験が悪いので、トースト通知への置き換えを推奨します。
- **`GitHub Ready` バッジが常時点灯**：実際の接続状態と連動していない固定表示です。
- 日本語UIのため `lang="ja"` は良いですが、フォントスタックの指定（`font-sans` のみ）で日本語フォントのフォールバックを明示するとよいです。

4. HTMLにカードA（shaインジケータ）とカードCを追加し、`fetch` とクエリ受け取りを実装する。

### 30分タイマーの実現方法（3案）

**案A：Cloudflare Cron Triggers + KV/D1（推奨）**

- 会話のたびに、Worker経由で「最終メッセージ時刻」と会話ログをKV（またはD1）に保存します。
- Cron Triggersで5分ごとにWorkerを起動し、「最終メッセージから30分以上経過、かつ未要約」の会話を探して要約を生成し、GitHubに書き込みます。
- アプリを閉じても動作するのが最大の利点です。30分ちょうどではなく最大5分程度の誤差が出ますが、実用上は問題ありません。

**案B：Durable Objects のアラーム**

- 会話ごとに1つのDurable Objectを作り、メッセージが来るたびにアラームを「今から30分後」に再設定（上書き）します。
- 時刻が正確で、会話単位の管理もきれいです。ただし実装がやや複雑で、有料プラン（Workers Paid）が必要になる場合があります。

**案C：フロント側タイマー（非推奨）**

- PWAがタブを閉じたりバックグラウンドに回ると止まるため、スマホでは信頼できません。

### 実装フロー（案Aの場合）

1. PWAのチャット画面でメッセージ送信 → Workerが Gemini API を呼び出す。
2. Workerが会話ログと `lastMessageAt` をKVに保存する。
3. Cronが定期実行され、30分以上更新がない未要約の会話を検出する。
4. Geminiに会話全体を要約させる（要約専用のプロンプト）。
5. 既存の「セーフティPull & Push」を使い、デイリーノートの専用セクション（例：`## AI Chats`）に追記する。
6. KVの会話に `summarized: true` を付ける。その後に同じ会話が再開された場合は新しいセッションとして扱うか、追記要約にするかを決めます。

### 仕様として決めておきたいこと

- **会話の区切り**：「最後の会話から30分」でセッションを分けるのか、手動の「新規チャット」ボタンも設けるのか。
- **要約の書き込み先の日付**：会話が日をまたいだ場合、開始日か終了日か。JST基準で決めてください。
- **要約フォーマット**：タイトル、要点の箇条書き、決定事項・TODO、元会話へのリンクなど。TODOを抽出してカレンダー機能と連携することもできます。
- **全文ログの保存**：要約のみか、全文も別ファイル（例：`40_ai_chats/`）に保存してリンクするか。要約の精度検証のために全文保存はおすすめです。
- **使うAPI**：Gemini API（Google AI Studio のキー）をWorker Secretsに保存します。無料枠の利用規約やレート制限も確認してください。
- **セキュリティ**：チャット内容は機微な情報を含みやすいため、前回指摘した認証（Cloudflare Access等）は必須になります。

### 補足

- Gemini公式アプリ（gemini.google.com）の会話は外部から取得できないため、「geminiとの対話画面を実装」とは、**このPWA内にGemini API経由のチャットUIを作る**という理解で合っていますか？ もし公式アプリでの会話も対象にしたい場合は、エクスポートや共有リンクを貼り付ける運用など、別の方法が必要です。
- 会話が非常に長い場合は、要約時に入力トークン上限を超えないよう、古い部分を段階的に要約する処理も検討してください。
