# システム仕様書 v3：スマートライフスタイル管理システム

在庫管理の自動化と、買い物・献立の迷いの解消を目的とした家庭向けシステムの仕様書（改訂版）。v2の検証A・検証Bを終え、MVP（入庫 ➔ 出庫 ➔ 補充リスト）を実装した時点の内容を反映している。

- 改訂日：2026-10-29
- 状態の表記：【実装済】【未実装】【暫定】（実装したが検証や見直しが必要）【未決】
- 実装の詳細・運用手順は別紙「引継ぎ資料」を参照する。

## 1. システム概要・目的

### 目的

- 在庫管理の入力・運用負荷を極限までゼロに近づける。
- 名もなき家事（食材の管理・献立決め・買い物の迷い）をシステムとAIで軽くし、日々の生活の質を高める。
- 第一目標は「在庫管理を容易にすること」。使われなくなることが最大のリスクなので、すべての設計判断で入力の手軽さと応答性を優先する。

### コアコンセプト

「レシートで入庫 ➔ キッチン前でポチポチ出庫 ➔ 在庫から導く提案と最短ルートでお買い物」という、人間の物理的動線に一致したローフリクション・アーキテクチャ。

### v2からの主な変更点

- **AIエンジンをClaude APIからGemini API（3.5 Flash基準）へ変更した。** 503・404などで使えない場合に備え、別バージョンへ自動で切り替える。
- **入庫の入力を「レシートの写真撮影」にした。** 写真をそのままGeminiに渡し、読み取り（OCR）と名寄せを1回の呼び出しで行う。別アプリのOCRとの連携（v2の項目11）は不要になった。
- 検証A・Bを完了し、出庫は「楽観的UI更新＋バッチ送信＋追記型ログ」の方式を採用した。
- 数量モデルを暫定決定した（個数、0.5刻み）。
- 「要補充」の判定基準を暫定決定した（品目ごとの最低在庫以下）。
- MVPを実装した（入庫・出庫・補充リストの3画面）。

## 2. 設計方針

1. **食材ベースを土台にする**：在庫と出庫は食材単位で扱い、レシピや料理名の入力を人間に求めない。
2. **レシピは使い捨ての仮説**：献立は確定した予定ではなく提案であり、採用しなくても何も起きない。
3. **人間に聞かず、システムが推定する**：名寄せなどは、まず別名テーブルとAIで推定し、確信度が低いものだけ確認する。
4. **粗い粒度から始める**：品目は「豚肉」「鶏肉」「葉物野菜」など粗めに設定し、必要になった時点で細分化する。
5. **失敗しても在庫操作は成功させる**：AI呼び出しの失敗が、入庫・出庫の操作を妨げない。
   - 出庫：AIを使わないため、この方針を満たしている【実装済】。
   - 入庫：AIが全モデルで失敗すると登録できない。手動で入庫する手段がなく、方針を満たしていない【未実装・要対応】（§8 項目25）。

## 3. コア機能要件

### ① 入庫管理【実装済】

#### 入力から登録までの流れ

1. 入庫画面で「レシートを撮影する」を押し、写真を撮る（端末のカメラが起動する）。
2. 端末側で写真を長辺2200pxのJPEGに縮小し、サーバー（GAS）経由でGeminiへ送る。
3. Geminiが、店名・購入日・合計金額と、品目行ごとの情報（品名の原文、部門コード、購入数、行金額、品目、確信度）をJSONで返す。
4. サーバーが、別名テーブルとの完全一致を優先して品目を確定し、確認画面用のデータを返す。
5. 利用者が確認画面で必要な行だけ直し、「登録する」を押す。
6. 入庫ログ・別名テーブル・品目マスタを更新する。

- 取得する情報は、品名、購入数、購入日の3つが基本。重量は取得しない。購入数は「2コ×単258」のような表記から読み取り、表記がなければ1とする。
- 食材以外（日用品・袋代・値引き行・お菓子・飲料など）は「対象外」として在庫に入れない。
- テキスト貼り付けによる入庫は実装していない【未実装】。

#### 名寄せ（表記揺れ対応）の構成

1. **別名テーブルで完全一致**：全角半角・ひらがなカタカナ・記号・空白を正規化したうえで、レシート表記（「ﾌﾞﾀｺﾏ」「豚小間切」など）を品目へ引く。ヒットした行は確信度1として扱い、AIの判定より優先する。
2. **未ヒット行はGeminiが判定**：品目マスタの一覧と一緒に画像を渡し、「どの品目か / 新規か / 対象外か」と確信度をJSONで返させる。マスタにない名前を返した場合は「新規」として扱う。
3. **確認UIに回す条件**：確信度が0.8未満の行、または新規品目の行。全件確認はしない。
4. **確定結果を別名テーブルへ自動追記**：利用者が確認した最終結果を学習する。既存の別名と違う品目に直した場合は上書きする。

実装上は、v2の「別名テーブル → Claude」を「別名テーブル → Gemini（部門コードをヒントとして渡す）」に置き換えた形である。部門コードを使った区分の自動学習は未実装【未実装】。

> **注意**：検証Bはv2の構成（Claude `claude-haiku-5-5`、テキスト入力）で実施した。本番のGemini＋写真入力では名寄せの精度を測っていない【未検証】。§7・§8 項目26を参照。

#### 確認画面【実装済】

| 区分 | 対象 | 初期状態 |
| --- | --- | --- |
| 確認が必要 | 確信度0.8未満、または新規品目の行 | 開いている |
| そのまま登録 | 確信度が高く、管理対象と判定した行 | 折りたたみ |
| 管理外と判断 | 確信度が高く、対象外と判定した行 | 折りたたみ。違うものだけ品目を選び直す。放置すれば管理外のまま確定する |

- 各行で、品目の選択（既存品目 / 新規品目 / 管理外）と数量を変更できる。新規品目のときは品目名と保管場所を入力する。
- 管理外側を折りたたみで確認する理由：管理対象を誤って管理外にすると、気づかないまま在庫が欠ける。逆の誤りは余分なカードが出るだけで、本人が0にして消せる。
- 参考表示として、読み取った行金額の合計と、レシートの合計金額を並べる。自動での検算判定は行っていない（§8 項目23）。

#### 管理対象の基準と保管場所（決定・【実装済】）

管理対象は「冷蔵庫に入るもの」ではなく、**調理に使う生鮮食材全般**とする。品目マスタの「区分」で次の扱いにする。

| 区分 | 対象の例 | 出庫UIでの扱い | 期限アラート |
| --- | --- | --- | --- |
| 冷蔵 | 肉、魚、乳製品、葉物野菜、納豆 | 主画面（初期表示のタブ） | 未実装 |
| 冷凍 | 冷凍食品、冷凍肉 | タブで切り替え | 対象外（案） |
| 常温 | 玉ねぎ、じゃがいも、バナナ | タブで切り替え | 未定 |
| 管理外 | お菓子、飲料、日用品 | 表示しない（在庫に入れない） | なし |

- 新規品目の保管場所は、Geminiの推定または利用者の選択で決め、品目マスタに書き込む。
- 区分の判定順は、別名テーブル、Gemini（部門コードをヒントに使う）。確定した区分は品目マスタに保存される。

#### 入庫時の数量の扱い【暫定】

- 数量は**個数（購入数）をそのまま在庫に加算**する。1パックを100%とする割合モデルと、標準入数マスタ（例：玉ねぎ1袋＝3個）は実装していない【未実装】。
- 品目は汎用名で登録する（例：牛豚合挽肉は「挽肉」）。

### ② 出庫管理（動的UIによるポチポチ減算）【実装済】

- **動的UI**：在庫が0より大きい食材のカードだけを、選択中の保管場所（冷蔵 / 冷凍 / 常温）のタブに表示する。残量が0になったカードは自動で消える。
- **ワンタップ減算**：「−1」「−½」「全部」の3ボタン。料理名の入力は不要。在庫を超えて減らない。
- **数量UI**：固定ボタン方式を採用【暫定】。ボタン定義は1か所（`ACTIONS`）で、割合UIなどに差し替えられる。
- **取り消し（Undo）**：直前の操作を1タップで取り消せる。取り消し履歴は端末のメモリ上にあり、画面を再読み込みすると消える。
- **再読込**：サーバーの在庫で画面を合わせ直す。未送信の操作があるときは、送信後に行うよう案内する。

#### 応答性の方式（検証Aで採用を決定）

| 項目 | 方針 |
| --- | --- |
| 画面反映 | タップ時点で画面上の数量を即時更新する（楽観的UI更新） |
| 初回表示 | 在庫データをHTMLに埋め込み、起動後の読み込み往復をなくす |
| 書き込み | タップをキューに溜め、最初のタップから約1.2秒後にまとめて送信する |
| 保存形式 | セルの上書きではなく、1操作1行の追記型ログ |
| 失敗時 | 未送信キューを端末のlocalStorageに保持し、待ち時間を延ばしながら自動リトライ（最大30秒間隔）。再読み込み後も送信を再開する |
| 二重送信 | 操作ごとのopIdで、サーバー側が重複を無視する |

目標値：タップから画面反映まで100ms未満、起動から初回表示まで2〜3秒以内。検証Aの結果は「実用上問題ない」と判断した（§7）。

### ③ 自動補充リストと買い物ナビ

- **補充リスト**【実装済・暫定】：在庫が品目マスタの「最低在庫」以下の品目を、保管場所順・名前順に表示する。最低在庫が空なら0として扱う（在庫ゼロで候補になる）。タップで取り消し線（買った印）を付けられるが、この印は端末のメモリ上のみで保持する。
- **旬のレコメンド**【未実装】：季節（月）と嗜好を踏まえ、「今週の旬の食材」を1〜2個だけ混ぜる。
- **ゾーン順の並べ替え**【未実装】：買い出しリストを、よく行くスーパーのゾーン順（入口からレジまで）に並べる。実態は最短経路計算ではなく、ゾーン順の並べ替えとして扱う。

### ④ 献立提案（MVP後）【未実装】

#### 型（テンプレート）モデル

レシピ（分量・手順）は持たず、「何が揃えば成立するか」だけを定義する。

- 型 = **必須ベース + 選択ベース + 自由枠**
- 例：カレー = 必須（ルー、肉、玉ねぎ、にんじん、じゃがいも）／自由枠（なす、きのこ、トマトなど）
- 例：鍋 = 必須（肉）／選択（白菜 or キャベツ）、きのこ、長ネギ／自由枠（ほぼ何でも）
- 肉の指定は「種類不問」と「鶏肉のみ」を型側で区別できるようにする。

#### 提案の出し方

買い物前に、見たいときだけ開く画面で次を表示する。

1. **成立済みの型**：今の在庫でベースが揃っているもの（最大2〜3型）。
2. **あと一歩の型**：不足ベースが1〜2個のもの。採用した場合のみ、不足食材が買い物リストに入る。
3. **自由枠の候補**：型ごとに、在庫から足せるものを2〜3個。余りものや旬の食材を優先する。

提案は1〜3個に絞り、「別の案」ボタンを用意する。

#### 型の作成

- 初期セットはAIに「家庭の定番20型」を生成させ、人間が取捨選択する。
- 追加は「麻婆なす作りたい」のような指示から、AIが型に変換して登録する。
- 自由枠はルール化せず、AIが在庫から判定する。

#### 作った料理の推定

- 出庫時に料理名は入力しない。
- 同じ時間帯（例：1〜2時間以内）の出庫を1つの「調理セッション」とみなし、材料の組み合わせからAIが型を推定する。どの型にも当てはまらなければ「不明」のままにする。
- 補助情報として、提案の採用履歴と、低確信度のときだけ表示する任意のワンタップ確認（「今日はカレーでしたか？」）を使う。
- 推定は夜間バッチ、または提案画面を開いた時に実行し、出庫の応答性に影響させない。
- 推定結果は履歴の参考情報であり、確定情報ではない。主な用途は、同じ型が続くのを避けることである。
- 出庫ログに日時と品目が残っているため、この機能は後から追加できる。

## 4. システムアーキテクチャ・技術スタック

```
[ フロントエンド ] ──(HTTP)──> [ バックエンド ] ──(API)──> [ AIエンジン ]
 スマホ / タブレット          Google Apps Script (GAS)      Gemini API
 (出庫・入庫・補充の3画面)    (集計・名寄せ・ログ追記)       (レシート読み取り・名寄せ)
                                   │
                                   └──> [ データベース ]
                                        Googleスプレッドシート
```

- **バックエンド**：Google Apps Script（スプレッドシートに紐づくスクリプト）。サーバーレスでランニングコストがほぼゼロ。
- **データベース**：Googleスプレッドシート（品目マスタ、別名、ログ）。
- **AIエンジン**：Gemini API（`generativelanguage.googleapis.com`、`generateContent`）。
  - 基準モデルは `gemini-3.5-flash`。
  - 次の順に試す：`gemini-3.5-flash` → `gemini-3.6-flash` → `gemini-3.5-flash-lite` → `gemini-3.1-flash-lite`。
  - 200以外のときの動き：429・5xx・通信エラーは同じモデルを1.5秒待って1回再試行し、駄目なら次のモデルへ。404・400・403は使えないモデルとみなして次へ。401はキー不正として即エラー。応答がJSONとして読めない場合も次のモデルへ。
  - 出力は `responseMimeType: application/json`、`temperature: 0`。
  - 将来の用途：旬の食材選定、献立提案、調理セッションからの型推定、買い物リストの最適化。
- **フロントエンド**：GASの`doGet()`でデプロイするウェブアプリ（HTML / JavaScript / CSS、1ファイル）。PWA化は未検討【未決】。

## 5. データ設計

- **追記型ログを正とする**：入庫・出庫を1操作1行で追記し、在庫は集計（品目ごとの増減の合計、下限0）で求める。競合に強く、Undoは逆符号の行の追記で実現する。

### シート定義【実装済】

| シート | 列 | 備考 |
| --- | --- | --- |
| 品目マスタ | 品目 / 区分（冷蔵・冷凍・常温・管理外） / 最低在庫 | 新規品目は入庫確定時に追記される（最低在庫は0） |
| 別名 | 別名（レシート表記の原文） / 品目（「対象外」も可） / 店名 | 照合時に正規化する。店名は記録のみで、照合には使わない |
| ログ | 日時 / 品目 / 増減 / opId / 端末 / 種別（入庫・出庫） | 入庫の日時は購入日の12:00（日本時間）。購入日が不明なら登録時刻 |

- opIdの形式：出庫は「端末ID-連番-時刻」、入庫は「レシートID-行番号」。直近500行の範囲で重複を無視する。
- 在庫（集計結果）のシートは持たず、画面表示のたびにログから集計する。履歴が増えたときの性能とアーカイブ方針は未決【未決】。
- 型定義・ゾーン定義のシートは、後続機能で追加する。

## 6. データフロー・運用シナリオ

1. **【買う】** スーパーで買い物 ➔ 入庫画面でレシートを撮影 ➔ 低確信度・新規の行だけ確認して登録。
2. **【作る】** 冷蔵庫から食材を取り出す ➔ 出庫画面で使った分だけポチポチ。在庫は即時に画面へ反映され、書き込みは裏で行われる。
3. **【補う】** 買い物前にスマホを開く ➔ 補充画面で要補充アイテムを確認（旬のおすすめ、作れる型の提案、ゾーン順ルートは後続）。

### 検証結果の記録

- **検証A**：タップから画面反映・書き込み完了までの時間は「実用上問題ない」と判断した。具体的な数値は記録していない。次回の計測時に、タップ→画面反映、タップ→書き込み完了、起動→初回表示（コールド / ウォーム）を本書に追記する。
- **検証B**：「問題なし」と判断した。誤統合率、静かな誤り、確認UIに回る行数などの数値は記録していない。
- **未確認の項目**：高速連打、複数端末の同時操作、機内モード中のタップでデータ欠損が出ないか。数量UIごとの操作のしやすさの比較。
- **本番のGemini＋写真入力での名寄せ精度**：未測定。実レシートで評価する必要がある（§8 項目26）。

### 検証項目（再掲：今後の評価に使う）

**出庫**：タップ→画面反映の時間 / タップ→書き込み完了の時間 / 起動→初回表示の時間 / 高速連打・複数端末・機内モードでの欠損 / 数量UIの操作性。

**入庫・名寄せ**：正解率 / **誤統合率**（別物を同じ品目にしてしまう割合。在庫が静かに狂うため最重要）/ **確認なしで確定した誤り** / 食材以外の除外精度 / 確認UIに回る行数（目安は1枚あたり数行以内）/ 2周目での別名テーブルのヒット率 / 写真の読み取りミス（行の欠落・数量の誤読）。

### 決定待ち・要検証（v2から継続）

2. **品目の粒度**：「豚こま」と「豚バラ」を同じ「豚肉」にするかなど。型の設計時に再確認する。
4. **賞味期限・消費期限の管理**：未対応。食品ロス削減や期限が近い食材を優先する提案には必要になる。
5. **在庫のズレの補正**：ポチポチの押し忘れで実在庫とずれていく。棚卸しや手動修正の画面が未実装【要対応】。
6. **調理セッションの区切りと推定精度**：時間間隔での区切りでは、朝食と夕食、作り置きの同時調理などの境界が曖昧になる。推定は後続に回す方針で確定してよいか最終確認が必要。
7. **提案の採用 = 作る、とみなす運用**：実際の買い物の流れに合うか未確認。
8. **GASの制約**：実行時間（1回6分）、UrlFetchの上限、同時アクセス時の競合（LockServiceを使用中）、履歴増加に伴う性能低下とアーカイブ方針。
10. **PWA化**：GASのWebアプリはiframe配信のため、Service Workerやマニフェストの配置に制限があり、完全なPWA化は難しい可能性がある。オフライン時の挙動も未定義。
12. **利用者と権限**：個人利用か家族利用か。Googleアカウントによるアクセス制限と、同時操作の扱い。
13. **スーパーのゾーン定義**：登録方法（手入力かAI推定か）、複数店舗への対応、品目と売場ゾーンの紐付けルール。
14. **嗜好・アレルギー・食事制限**：嗜好データの蓄積方法。アレルギーや食事制限は安全面から、旬レコメンドと献立提案の双方で考慮が必要。
15. **プライバシー**：レシート画像をGemini APIへ送信している。無料枠と有料枠で入力データの扱いが異なる可能性があるため、利用規約を確認し、方針を決める【要確認】。
16. **成功指標（KPI）**：継続率や出庫入力率など、ローフリクションが達成できたかの測り方。

### 入庫・保管場所まわり（v2から継続）

17. **部門コードの汎用性**：現状はGeminiへのヒント渡しのみ。店ごとのコード表を自動学習にするか手入力にするかを決める。
18. **惣菜・味付け済み品の扱い**：管理対象にするか、確認UIで拾う運用にするかが未定。
19. **冷凍・常温の期限アラート**：冷凍は対象外とする案。常温の青果を対象にするかは未定。
20. **調味料・米・油など常温の定番品**：管理外にするか、補充リストのみで扱うかが未定。
21. **標準入数マスタ**：割合モデルを導入する場合に必要。初期値の作り方と、ズレたときの補正のしやすさを検証する。
22. **レシート品名の途中切れと汎用すぎる品名**：「ミニずっしりデニッ」「鮮魚」のような行を、写真入力で扱えるか確認する。
23. **行金額による検算**：行金額の合計に内税額を足すと合計に一致する店がある。現状は並べて表示するだけ。自動で読み取りミスを検知できるか検証する。
24. **検証のサンプル数**：週2回の買い物では集まるまで時間がかかる。まず10枚前後で一度評価し、過去のレシートが残っていれば併用する。

### 追加（v3）

25. **AI障害時の手動入庫**：Geminiが全モデルで失敗すると入庫できない（設計方針5の未達）。品目と数量を手入力で登録する画面が必要【要対応】。
26. **Geminiでの名寄せ精度が未測定**：検証BはClaude・テキスト入力で実施した。本番のGemini・写真入力で、検証Bと同じ指標を測り直す【要対応】。判定の傾向（特に別物を統合しすぎないか）がClaudeと同じとは限らない。
27. **ログの肥大化**：画面の初期表示と再読込のたびに、ログ全体を読み込んで集計している。件数が増えると遅くなる。集計シートへの移行、または古いログの繰越（品目ごとの残高を1行にまとめる）を検討する。
28. **別名の店別管理**：別名の照合は店名を見ない。同じ表記が店によって別の品目を指す場合に誤統合する可能性がある。
29. **別名の誤学習**：確認UIに回らなかった行が誤っていても、別名テーブルへ登録される。誤りが固定される可能性がある（検証Bの「静かな誤り」と同じ問題）。別名テーブルの見直し手段を用意する。
30. **取り消し履歴と補充リストの「買った」印**：端末のメモリのみで保持しており、再読み込みで消える。
31. **日付と時刻**：購入日の時刻を日本時間の12:00に固定している。
32. **モデル名の変更への追随**：Geminiのモデル名や提供状況は変わりうる。404が増えた場合は、切り替えリスト（`MODELS`）を最新に更新する。
