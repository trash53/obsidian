## 2. 成果物

| ファイル | 役割 |
| --- | --- |

GASプロジェクトに置くファイルはこの2つだけ。HTMLファイルの名前は必ず小文字の `index`（コード内で `createTemplateFromFile('index')` と指定している）。検証用のコード（検証Aの `Code.gs`・`index.html`、検証Bの `Code_検証B.gs`）を同じプロジェクトに残すと、関数名・定数名が重なって、ファイル全体が読み込めなくなる（メニューも出なくなる）ので、別のプロジェクトに分ける。

検証用コードの位置づけ：検証Aは出庫の方式比較、検証Bは名寄せの3方式比較（実レシートの行を貼り、`結果`・`集計`シートに指標を出す）。Geminiでの名寄せを再評価するときは、検証Bのコードの `askClaude_` をGemini呼び出しに差し替えるのが近道。

## 3. 環境構築とデプロイ

1. 新しいGoogleスプレッドシートを作り、「拡張機能 → Apps Script」を開く。
2. `Code.gs` と `index.html` の内容を貼る（HTMLは「ファイルを追加 → HTML」で `index` を作る）。
3. **スプレッドシートを再読み込み**（ブラウザのF5）し、メニュー「在庫管理」が出ることを確認する。メニューは、スプレッドシートを開いたとき（`onOpen`）にしか作られない。**ウェブアプリの画面には、このメニューは出ない。**
4. メニュー「在庫管理 → 初期セットアップ」を実行する。次のシートができる（既存のシートは消さない）。
   - `品目マスタ`（サンプル16品目と仮の売り場）、`別名`、`ログ`
   - `売り場順`（仮の並び）、`部門コード`（A列は文字列形式）
   - `型`、`補充除外`、`採用`
   - 売り場列のない古い品目マスタには、売り場の列を足す（`migrateMaster_`）。
5. Gemini APIキーを設定する。メニュー「Gemini APIキーを設定」か、「プロジェクトの設定 → スクリプト プロパティ」で `GEMINI_API_KEY` を追加する。
6. エディタで `testGemini` を実行し、実行ログに `OK: gemini-3.5-flash …` のように出ることを確認する（キーとモデルの切り分け）。初回はUrlFetchなどの権限承認が出る。
7. メニュー「在庫管理 → 型を生成（AI）」を実行して、型シートに定番の型を作る。要らない行は「有効」の○を消す。
8. `売り場順` シートを、よく行くスーパーの売り場の並びに直す。品目マスタの売り場列と、最低在庫を見直す（§4）。
9. 「デプロイ → 新しいデプロイ → ウェブアプリ」で公開する。
10. 発行されたURLをスマホ・PCで開く。

**コードを直したあとは、必ず新しいバージョンで再デプロイする**（デプロイを管理 → 鉛筆アイコン → バージョン：新バージョン → デプロイ）。ウェブアプリのURLは、デプロイ時点のバージョンを配信する。

**エディタの「実行」ボタンで動かしてよい関数**：`setup`、`testGemini`、`generateTemplates`。それ以外の、画面から引数付きで呼ばれる関数（`appendLogs`・`parseReceipt`・`commitReceipt`・`adjustStock`・`draftTemplate`・`saveTemplate`・`setShopExclude`・`setAdopt` など）は、エディタから動かすとエラーになる。`setApiKey` はダイアログを使うので、エディタからは動かず（`Cannot call SpreadsheetApp.getUi() from this context`）、スプレッドシートのメニューから実行する。

初期在庫の入れ方：補正タブで現在数を入力する（在庫0の品目も出る）。または入庫画面で登録する。`ログ` シートに「日時 / 品目 / 増減 / opId（一意な文字列）/ 端末 / 補正」の行を直接追加してもよい。

## 4. データ構造

| シート | 列 |
| --- | --- |
| 品目マスタ | 品目 / 区分（冷蔵・冷凍・常温・管理外） / 最低在庫 / 売り場 |
| 別名 | 別名（レシート表記の原文） / 品目（「対象外」も可） / 店名 |
| ログ | 日時 / 品目 / 増減 / opId / 端末 / 種別（入庫・出庫・補正） |
| 売り場順 | 売り場 / 順（補充リストの並び順。小さいほど入口に近い） |
| 部門コード | コード / 売り場 / 件数 / 品目例 / 店名（レシートの部門コードの観測記録。売り場の列だけ人が埋める） |
| 型 | 型 / 必須 / 選択 / 有効 / 備考 |
| 補充除外 | 品目 / 日時 |
| 採用 | 型 / 日時 |

- 在庫 = ログの品目別の増減合計（下限0、小数第2位まで）。在庫専用のシートはない。
- 区分が「管理外」の品目は、在庫画面に出さない。
- **最低在庫が空欄の品目は、補充リストに自動では載らない**。数字（0を含む）が入った品目だけが、在庫がその数以下で載る。新規品目は空欄で作られる。
- 別名の照合は、正規化（全角半角・ひらがなカタカナ・記号・空白をならす）した文字列で行う。正規化の実装は `norm_`（画面側は `norm`。同じ内容）。
- ログの重複排除は、直近500行の範囲のopIdで行う（`DEDUPE_WINDOW`）。
- 売り場順に無い売り場名は、未設定扱い（並びは最後）。
- 部門コードの割り当て（売り場列）は、新規品目の売り場の自動決定に使う。優先順は、部門コードの割り当て、Geminiの推定、未設定。
- 型の材料は「、」区切り。「豚肉|鶏肉|挽肉」は「どれか1つ」。有効が空の行、必須が空の行は使わない。材料名は品目マスタの表記に揃える。
- 補充除外は、入庫（レシート・手動）で該当品目の行が自動で消える。補正では消えない。
- 採用は、型が成立する（必須の不足がなくなる）と、画面側の処理で自動で消える。

## 5. コード構成

### Code.gs

| 関数 | 役割 |
| --- | --- |
| `onOpen` / `setup` / `migrateMaster_` / `setApiKey` | メニュー、初期シート作成、売り場列の追加、APIキー保存 |
| `doGet` | 画面を返す。在庫・売り場・型・採用をJSONにしてHTMLへ埋め込む（初回表示の高速化） |
| `getStock` / `getStock_` / `sums_` | 在庫の集計。品目ごとに売り場、売り場の順、最低在庫（空はnull）、除外中かを付けて返す。`sums_`は下限0を掛けない生の合計 |
| `appendLogs` / `appendRows_` | 出庫のログ追記（ロック、opIdによる重複排除） |
| `parseReceipt` | 写真をGeminiで読み取り、別名テーブルを優先して確認画面用の行を返す（部門コード・売り場の推定を含む） |
| `commitReceipt` | 確認済みの行を入庫ログに追記し、別名・品目マスタ・売り場を更新し、補充の除外を解除する。手動入庫もこれを使う |
| `recordDept_` | レシートの部門コードを部門コードシートへ記録する（再送では数え直さない） |
| `adjustStock` | 在庫の補正。現在数との差分を「補正」行として追記する |
| `getSuggestions` | 成立済み・あと一歩の型を判定して返す（AIは使わない）。型の定義（`defs`）も返す |
| `loadTypes_` / `parseGroups_` | 型シートの読み込み、「豚肉\|鶏肉、玉ねぎ」の解析 |
| `generateTemplates` | メニューから実行。Geminiで型を生成して型シートへ追記 |
| `draftTemplate` / `saveTemplate` / `clean_` | 一言から型の下書きを作る／確認済みの型を登録する（同名は上書き）／セルに書く文字列の整形 |
| `setShopExclude` / `setAdopt` / `toggleList_` / `loadList_` / `removeFromList_` / `ensureSheet_` | 補充の除外・型の採用の保存と、シートの補助 |
| `callGemini_` | Geminiの呼び出し。リトライとモデルの切り替えを担当 |
| `testGemini` | エディタ実行用の疎通確認 |
| `readRows_` / `loadAlias_` / `loadAreas_` / `loadDept_` / `norm_` | 補助関数 |

主な定数：`MODELS`（試すモデルの順序）、`CONF_TH`（確認に回す確信度のしきい値、0.8）、`ZONES`、`DEDUPE_WINDOW`、`AREA_UNSET`（売り場未設定の並び順、999）、`DEFAULT_AREAS`・`DEFAULT_ITEM_AREA`（売り場の初期値）、`SUGGEST_MAX_MISSING`（あと一歩とみなす不足数、2）、`TYPE_RULES`（型の生成ルール）。

### index.html

- 5つのセクション：出庫（`#vOut`）、入庫（`#vIn`）、補充（`#vShop`）、補正（`#vAdj`）、献立（`#vMenu`）。ヘッダーのタブで切り替える（`show`関数）。
- 出庫：`ACTIONS`（数量ボタン定義）、`act`（楽観的更新とキュー追加）、`flush`（まとめて送信、失敗時は再試行）、`persist` / `restore`（未送信キューをlocalStorageに保存・復元）。カードの数量のタップで補正タブへ。
- 入庫：`shrink`（写真を長辺2200pxのJPEGに縮小）、`renderReview`（確認画面）、確認ボタンの登録処理、`applyIn`（登録した行を画面の在庫へ反映）。手動入庫は、下部の `#manual`（`renderManual`）。
- 補充：`renderShop`（常備品の不足＋採用した型の不足を、売り場順に表示。除外中は折りたたみ）、`setEx`（除外・戻す）、`setAdopt`（採用・取り下げ）。
- 補正：`renderAdj`、`markAdj`。
- 献立：`loadSug` / `renderSug`（提案の読み込みと表示）、`showDraft` ほか（型を追加する欄）。
- 共通：`sync`（サーバーの在庫で画面を合わせ直す）、`refresh`（静かに同期する）、`reload`。
- 先頭の別の `<script>` が、実行時エラーを画面上部のステータス欄に表示する。画面が動かないときの切り分けに使う。

## 6. 主要な設計判断とその理由

| 判断 | 理由 |
| --- | --- |
| 追記型ログを正とし、在庫は集計で求める | 競合に強い。Undoは逆符号の行の追記で済む。型推定に使う日時・品目も残る |
| 補正も「補正」行の追記にする | 履歴が残り、どの品目がよくずれるか後で見られる。差分はサーバー側で、ログの生の合計から求める（下限0で隠れたマイナスがあっても合う） |
| 出庫は楽観的更新＋バッチ送信 | 検証Aで応答性が実用上問題ないと確認。連続タップでも画面が止まらない |
| 入庫の確認は低確信度・新規の行のみ | 全件確認は運用負荷が高く、使われなくなるリスクが最大 |
| 管理外の確認は折りたたみ（違うものだけ直す） | 管理対象を誤って管理外にすると、気づかないまま在庫が欠ける |
| 別名テーブルを優先し、AIの結果より先に採用 | 命中すればAI呼び出しの誤りを避けられる。使うほど命中率が上がる |
| 写真をGeminiへ直接渡す（別アプリのOCRを使わない） | 手順が減る。読み取りと名寄せを1回の呼び出しで行える |
| Geminiのモデルを複数用意し、順に試す | 503（過負荷）や404（モデルの廃止・名称変更）でも入庫を止めないため |
| ログの`opId`を「レシートID-行番号」などにする | 通信失敗後に「登録する」を押し直しても二重登録にならない（手動入庫・補正も同様） |
| 手動入庫は`commitReceipt`を流用する | 登録処理を2つ持たない。レシート表記が空なら、別名には学習されない |
| 売り場は日本語名で持ち、部門コードは割り当ての補助にする | サンプルが少ないうちはコードだけでは決められない。コードの観測記録は自動で貯まり、あとから割り当てを埋めるだけでコード管理に寄せられる |
| 売り場の誤りは品目マスタで直す（確認画面には出さない） | 影響が並び順だけで、確認の手間を増やす価値が低い |
| 最低在庫が空欄なら補充に載せない | 一度買っただけの品目や季節品が、切れるたびに載るのを避ける。常備品だけ数字を入れる運用にする |
| 除外は入庫で解除し、補正では解除しない | 入庫は買った事実。補正は数え直しで、買ったとは限らない |
| 献立の不足は「採用した型」だけ補充に入れる | あと一歩の型を全部載せると、補充リストが献立の不足で埋まる |
| 型の判定はAIを使わず在庫から機械的に行う | 速く、結果が毎回同じ。AIは型の生成・追加だけに使う |
| 型の書式は「、」区切り＋「\|」（どれか1つ） | シート上で人が読み書きでき、肉の種類を問わない型も鶏肉のみの型も同じ書式で表せる |
| 型の追加は、AIの下書きを確認・修正してから登録 | AIの変換結果をそのまま登録しない |

## 7. 既知の制限・リスク

優先して対応を検討するものから順に並べる。詳細は仕様書 §8 の項目番号を参照。

1. **Geminiでの名寄せ精度が未測定・保留**（項目26）。検証Bで確認したのはClaude・テキスト入力の構成。誤認識が複数回出たら評価する。
2. **型の生成・追加のGemini応答が未確認**（項目39）。実環境で、必須の過不足や数を見て調整する。
3. **型の材料名とマスタ表記の不一致**（項目38）。表記がズレると、在庫があっても成立しない。
4. **提案の判定が2か所にある**（項目34）。サーバー（`getSuggestions`）と画面（`renderShop`）で規則が重複している。規則を変えるときは両方を直す。
5. **別名の誤学習が固定される**（項目29）。確認に回らなかった誤りが別名に登録される。修正は `別名` シートを手で編集する。
6. **ログ肥大化による性能低下**（項目27）。表示のたびにログ全体を集計している。補正も1行ずつ増える。
7. **プライバシー**（項目15）。レシート画像をGemini APIへ送信している。無料枠・有料枠のデータの扱いを確認する。
8. **部門コードは店ごとに区別しない**（項目35）。複数の店のレシートを入れると、割り当てが衝突する可能性がある。
9. 取り消し履歴と補充リストの「買った」印は、再読み込みで消える（項目30）。除外・採用はシートに保存される。
10. 検証A・Bの数値が未記録。

## 8. トラブルシューティング

| 症状 | 原因と対処 |
| --- | --- |
| スプレッドシートに「在庫管理」メニューが出ない | メニューは`onOpen`が作る。**スプレッドシートを再読み込み（F5）**する。ウェブアプリの画面には出ない。それでも出ないときは、エディタのファイル一覧に`Code.gs`と`index`の2つだけか、`Code.gs`が最後の関数（`getStock_`）まで貼れているか確認する。実行数（左のメニュー）の`onOpen`の行にエラーがないかも見る |
| `setApiKey`を実行して`Cannot call SpreadsheetApp.getUi() from this context` | エディタの実行ボタンから動かしたため。ダイアログは、スプレッドシートのメニューからしか動かない。または、プロジェクトの設定のスクリプト プロパティに`GEMINI_API_KEY`を直接追加する |
| エディタから`commitReceipt`・`parseReceipt`・`appendLogs`・`adjustStock`などを実行するとエラー | 画面から引数付きで呼ぶ関数のため、エディタの実行ボタンでは動かない。画面（ウェブアプリのURL）から操作する |
| 画面にタブとボタンだけが出て、カードや「同期済み」が出ない | スクリプトが実行されていない。デプロイ済みの `index.html` が最新か確認し、新バージョンで再デプロイする。ステータス欄にエラー文が出ていればそれを確認する |
| コードを直したのに反映されない | 再デプロイしていない。デプロイを管理 → 新バージョンでデプロイ |
| 画面に関数名（`setApiKey` など）が出る | `index.html` に `Code.gs` の内容が混ざっている。両ファイルの中身を確認し貼り直す。HTMLのファイル名は小文字の `index` |
| 読み取りで「すべてのモデルで失敗しました → …」 | 各モデルの失敗コードが並ぶ。`400`＋「API key not valid」→キーの誤り。`404`が並ぶ→モデル名が現行にない。`503`・`429`が並ぶ→混雑のため時間をおく。この間も、手動入庫で登録できる |
| `testGemini`・`generateTemplates`が失敗する | 同上。まずAPIキー（`GEMINI_API_KEY`）とモデル名（`MODELS`）を確認する |
| 在庫が増減しない、重複する | `ログ` シートのopIdを確認。同じopIdの行は追記されない設計 |
| 補充リストに品目が出ない | 最低在庫が空欄だと自動では載らない。除外中の品目は、リスト下の「除外中」にある。入庫すると戻る |
| 補充リストの売り場がすべて「売り場未設定」 | 品目マスタの売り場列が空、または`売り場順`シートにその売り場名がない。「初期セットアップ」を再実行し、売り場列と`売り場順`を確認する |
| 部門コードが`604`のように0が消える | `部門コード`シートのA列が文字列形式でない。A列を選び、書式を「書式なしテキスト」にする |
| 献立タブに「型が登録されていません」 | メニュー「型を生成（AI）」を実行する。または、型シートの「有効」の列に○があるか確認する |
| 献立で型が成立しない（材料はあるはず） | 型の材料名が品目マスタの表記と違う可能性。表記を揃える。選択肢は「豚肉\|鶏肉」のように書く |
| 補正が登録できない | 未送信の出庫がある。ステータスが「同期済み」になってから押す |
| 初回の画面表示が遅い | ログ件数が増えている可能性（項目27） |

## 9. 次にやること（推奨順）

1. **しばらく使って、提案に違和感がないかを見る**：型の数・材料名、売り場の割り当て、補充リストの行数、最低在庫の設定。
2. **自由枠のAI判定**：型ごとに、在庫から足せる食材を2〜3個、AIが選ぶ。提案が物足りないと感じてから着手する。
3. **旬のレコメンド**：補充リストに「今週の旬」を1〜2個混ぜる。旬のデータの持ち方（AIに聞くか、表を持つか）を決める。
4. **実レシートでの精度評価**：誤認識が複数回出たとき、Gemini・写真入力で、検証Bと同じ指標（正解率、誤統合、確認なしで確定した誤り、除外精度、確認UIに回る行数）を測る。数値を仕様書 §7 に記録する。
5. **調理セッションの型推定**：ログが数週間分たまってから。
6. **ログの集計方針**：件数が数千行になる前に、繰越行の導入などを決める。
7. **プライバシー方針の決定**（項目15）。

## 10. 次のAI（Claude等）との会話を再開するときの手順

1. 次のファイルを添付する：システム仕様書 v4、本書、`Code.gs`、`index.html`。
2. 「何を進めたいか」を1つに絞って伝える（例：「自由枠のAI判定を作りたい」）。
3. 変更を依頼したら、返ってきたファイルで差し替え、**新バージョンで再デプロイ**する。シートの追加がある変更のときは、メニューの「初期セットアップ」も実行する。
4. 画面が動かないときは、ステータス欄のエラー文と、エディタのファイル一覧（ファイル名）を伝える。
5. 仕様を変えたときは、仕様書 §8 の項目を更新して残す。
