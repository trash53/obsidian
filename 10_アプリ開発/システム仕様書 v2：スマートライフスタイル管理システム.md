# システム仕様書 v2：スマートライフスタイル管理システム

在庫管理の自動化と、買い物・献立の迷いの解消を目的とした家庭向けシステムの仕様書（改訂版）。栄養管理を対象外とし、応答性・名寄せ・献立提案の検討結果を反映している。

## 1. システム概要・目的

### 目的

- 在庫管理の入力・運用負荷を極限までゼロに近づける。
- 名もなき家事（食材の管理・献立決め・買い物の迷い）をシステムとAIで軽くし、日々の生活の質を高める。
- 第一目標は「在庫管理を容易にすること」。使われなくなることが最大のリスクなので、すべての設計判断で入力の手軽さと応答性を優先する。

### コアコンセプト

「レシートで入庫 ➔ キッチン前でポチポチ出庫 ➔ 在庫から導く提案と最短ルートでお買い物」という、人間の物理的動線に一致したローフリクション・アーキテクチャ。

### v1からの主な変更点

- 栄養・健康管理（PFC推計）を対象外とした。
- 出庫の応答性を最重要の設計課題とし、楽観的UI更新と追記型ログを採用した。
- レシートの表記揺れ対策（名寄せ）を独立した検証項目とした。
- 献立提案を「型（ベース＋自由枠）」モデルで定義し、MVP後の機能として位置づけた。

## 2. 設計方針

1. **食材ベースを土台にする**：在庫と出庫は食材単位で扱い、レシピや料理名の入力を人間に求めない。
2. **レシピは使い捨ての仮説**：献立は確定した予定ではなく提案であり、採用しなくても何も起きない。
3. **人間に聞かず、システムが推定する**：料理名や名寄せは、まずログとAIで推定し、確信度が低いものだけ確認する。
4. **粗い粒度から始める**：品目は「豚肉」「鶏肉」「葉物野菜」など粗めに設定し、必要になった時点で細分化する。
5. **失敗しても在庫操作は成功させる**：AI呼び出しの失敗が、入庫・出庫の操作を妨げない。

## 3. コア機能要件

### ① 入庫管理

- レシートの品目行を読み込み、購入した食材（品名・購入日）を在庫へ登録する。入力方法は写真またはテキスト。
- 店名と合計金額は別アプリのOCRで精度よく認識できることを確認済み。品目行の名寄せは別途検証する。
- 食材以外（日用品・袋代・値引き行）は除外する。
- 登録時に初期ステータス（初期残量、平均消費日数など）を付与する。

#### 名寄せ（表記揺れ対応）の構成

1. **別名テーブルで完全一致**：全角半角・記号・空白を正規化したうえで、「ﾌﾞﾀｺﾏ」「豚小間切」などを品目マスタへ引く。
2. **未ヒット行のみClaudeが判定**：マスタ一覧とレシート行を渡し、「どの品目か / 新規品目か / 食材以外か」と確信度をJSONで返させる。
3. **低確信度の行のみ確認UIに表示**：全件確認はしない。
4. **確定結果を別名テーブルへ自動追記**：使うほど手順1の命中率が上がり、Claude呼び出しが減る。

#### 管理対象の基準と保管場所（決定）

管理対象は「冷蔵庫に入るもの」ではなく、**調理に使う生鮮食材全般**とする。玉ねぎ、じゃがいも、バナナなどの常温品も在庫に入れ、補充リストと献立提案に反映する。品目マスタに保管場所の属性を持たせ、次の4区分で扱う。

| 区分 | 対象の例 | 出庫UIでの扱い | 期限アラート |
| --- | --- | --- | --- |
| 冷蔵 | 肉、魚、乳製品、葉物野菜、納豆 | 主画面に表示 | 対象 |
| 冷凍 | 冷凍食品、冷凍肉 | タブまたは区画を分けて表示 | 対象外（案。賞味期限が長いため） |
| 常温 | 玉ねぎ、じゃがいも、バナナ | タブまたは区画を分けて表示 | 未定（青果を対象にするか要検討） |
| 管理外 | お菓子、飲料、日用品 | 表示しない（在庫に入れない） | なし |

#### 区分の判定

- 判定順は、別名テーブル、部門コード、Claudeの順とする。
- レシートの行頭にある6桁の部門コードをヒントに使う。サンプル1枚からの推測では、000604が冷凍、000701〜707がお菓子、000620台が乳製品、000249・000253・000003が鮮魚系に見える。
- コードの意味は店ごとに異なるため、店ごとのコード表を別名テーブルと同じ要領で学習させる。
- 確定した区分は品目マスタに書き戻し、次回から同じ判定を繰り返さない。

#### 管理外判定の確認UI

- 管理外と判定した行を、入庫後に折りたたみで「次の○点は冷蔵庫外に置くものと判断しました。よろしいですか？」と表示する。
- 違うものだけ1タップで管理対象に戻す。放置すれば管理外のまま確定する。
- 修正結果は品目マスタと別名テーブルに書き戻す。
- 確認の対象を管理外側にする理由：管理対象を誤って管理外にすると、気づかないまま在庫が欠ける。逆の誤りは余分なカードが出るだけで、本人が0にして消せる。

#### 入庫時の数量の扱い（案。検証Aで確定）

- レシートには重さが表記されないため、重量は取得しない。栄養計算を対象外にしたので、グラム換算も不要である。
- 取得する情報は、品名、購入数、購入日の3つ。購入数は「2コ×単258」のような表記から読み取り、表記がなければ1とする。
- 1パックを100%として、出庫は割合で減算する。袋売りの野菜は、品目マスタの標準入数（例：玉ねぎ1袋＝3個）を初期値にし、実際と違えば出庫時に補正する。
- 品目は汎用名で登録する（例：牛豚合挽肉は「挽肉」）。別種のひき肉が庫内に何種類も並ぶ想定は薄いため、粗い粒度で足りる。

### ② 出庫管理（動的UIによるポチポチ減算）

- **動的UI**：在庫が0より大きい食材のカードだけを画面に表示する。残量が0になったカードは自動で消える。
- **ワンタップ減算**：調理中にキッチン近くの端末（スマホ・タブレット）で、使った分だけをタップして減らす。料理名の入力は不要で、名前のない料理や目分量の消費にも対応する。
- **数量UI**：個数、割合（少し / 半分 / 全部）、固定ボタン（−1 / −0.5）のうち、入力と減算が最も楽なものを検証で決める。数量UIは後から差し替えられる構造にする。
- **取り消し（Undo）**：直前の操作を1タップで取り消せる。

保管場所ごとの表示：冷蔵を主画面とし、冷凍と常温はタブまたは区画で分けて、冷蔵のカードが埋もれないようにする。

#### 応答性の要件

出庫は食材を1種ずつ入力する前提のため、ここが重いと使われなくなる。次の方式を採用する。

| 項目 | 方針 |
| --- | --- |
| 画面反映 | タップ時点で画面上の数量を即時更新する（楽観的UI更新） |
| 初回表示 | 在庫データをHTMLに埋め込み、起動後の読み込み往復をなくす |
| 書き込み | タップをキューに溜め、1〜2秒間隔でまとめて送信する |
| 保存形式 | セルの上書きではなく、1操作1行の追記型ログとする |
| 失敗時 | 未送信キューを端末側に保持し、自動リトライする |

目標値：タップから画面反映まで100ms未満、起動から初回表示まで2〜3秒以内。

### ③ 自動補充リストと買い物ナビ

- 在庫がゼロ、または要補充のアイテムを買い物リストの候補にする。
- Claudeが季節（月）と嗜好を踏まえ、「今週の旬の食材」を1〜2個だけレコメンドに混ぜる。
- 買い出しリストを、よく行くスーパーのゾーン順（入口からレジまで）に並べ替えて表示する。実態は最短経路計算ではなく、ゾーン順の並べ替えとして扱う。

### ④ 献立提案（MVP後）

#### 型（テンプレート）モデル

レシピ（分量・手順）は持たず、「何が揃えば成立するか」だけを定義する。

- 型 = **必須ベース + 選択ベース + 自由枠**
- 例：カレー = 必須（ルー、肉、玉ねぎ、にんじん、じゃがいも）／自由枠（なす、きのこ、トマトなど）
- 例：鍋 = 必須（肉）／選択（白菜 or キャベツ）、きのこ、長ネギ／自由枠（ほぼ何でも）
- 肉の指定は「種類不問」と「鶏肉のみ」を型側で区別できるようにする。

#### 提案の出し方

買い物前に、見たいときだけ開く画面で次を表示する。

1. **成立済みの型**：今の在庫でベースが揃っているもの（最大2〜3型）。
2. **あと一歩の型**：不足ベースが1〜2個のもの。採用した場合のみ、不足食材が買い物リストに入る。
3. **自由枠の候補**：型ごとに、在庫から足せるものを2〜3個。余りものや旬の食材を優先する。

提案は1〜3個に絞り、「別の案」ボタンを用意する。

#### 型の作成

- 初期セットはClaudeに「家庭の定番20型」を生成させ、人間が取捨選択する。
- 追加は「麻婆なす作りたい」のような指示から、Claudeが型に変換して登録する。
- 自由枠はルール化せず、Claudeが在庫から判定する。

#### 作った料理の推定

- 出庫時に料理名は入力しない。
- 同じ時間帯（例：1〜2時間以内）の出庫を1つの「調理セッション」とみなし、材料の組み合わせからClaudeが型を推定する。どの型にも当てはまらなければ「不明」のままにする。
- 補助情報として、提案の採用履歴と、低確信度のときだけ表示する任意のワンタップ確認（「今日はカレーでしたか？」）を使う。
- 推定は夜間バッチ、または提案画面を開いた時に実行し、出庫の応答性に影響させない。
- 推定結果は履歴の参考情報であり、確定情報ではない。主な用途は、同じ型が続くのを避けることである。

## 4. システムアーキテクチャ・技術スタック

```
[ フロントエンド ] ──(HTTP)──> [ バックエンド ] ──(API)──> [ AIエンジン ]
 スマホ / タブレット          Google Apps Script (GAS)      Claude API
 (動的UI・ポチポチ画面)       (ロジック・集計・ルーティング)  (名寄せ・旬・献立・型推定)
                                   │
                                   └──> [ データベース ]
                                        Googleスプレッドシート
```

- **バックエンド**：Google Apps Script。サーバーレスでランニングコストがほぼゼロ。
- **データベース**：Googleスプレッドシート。在庫、出庫・入庫ログ、品目マスタ、別名テーブル、型定義、ゾーン定義を管理する。
- **AIエンジン**：Claude API。用途は名寄せ判定、旬の食材選定、献立提案、調理セッションからの型推定、買い物リストの最適化。
- **フロントエンド**：GASの`doGet()`でデプロイする簡易Webアプリ（HTML / JavaScript / CSS）。PWA化は実現可能性の確認後に判断する。

## 5. データ設計の方針

- **追記型ログを正とする**：入庫・出庫を1操作1行で追記し、在庫は集計で求める。競合に強く、Undoは逆の行の追記で実現できる。
- **出庫ログの必須項目**：日時、品目、増減量。この2つ（日時・品目）が残っていれば、型の推定ロジックを後から追加できる。
- **別名テーブル**：表記揺れと品目マスタの対応を保持し、確定のたびに自動追記する。
- **シート構成（案）**：在庫（集計結果）、ログ、品目マスタ、別名、型定義、ゾーン定義。カラム定義は検証後に確定する。

## 6. データフロー・運用シナリオ

1. **【買う】** スーパーで買い物 ➔ レシートの品目行を名寄せして入庫。低確信度の行のみ確認。
2. **【作る】** 冷蔵庫から食材を取り出す ➔ 動的UIで使った分だけポチポチ出庫。在庫は即時に画面へ反映され、書き込みは裏で行われる。
3. **【補う】** 買い物前にスマホを開く ➔ 要補充アイテムと旬のおすすめが並び、（MVP後は）作れる型の提案も確認できる ➔ ゾーン順のルートで買い物して帰宅。

## 7. 開発ステップ

| 段階 | 内容 |
| --- | --- |
| 検証A | 出庫プロトタイプ：動的UIとスプレッドシート書き込みのみ。素朴な方式と、楽観的更新＋バッチ＋追記ログの方式を比較する |
| 検証B | 名寄せテスト：実レシート20〜30枚（3〜4店舗）で、別名テーブルのみ / Claudeのみ / 併用を比較する |
| MVP | 入庫 ➔ 出庫 ➔ 補充リストの順に実装する |
| 後続 | 旬のレコメンド、ゾーン順ルート、型による献立提案、調理セッションの型推定 |

検証Aと検証Bは独立しており、並行して進められる。

### 検証項目

**検証A（出庫）**

- タップから画面反映までの時間
- タップから書き込み完了までの時間
- 起動から初回表示までの時間（コールド / ウォーム別）
- 高速連打、複数端末の同時操作、機内モード中のタップでデータ欠損が出ないか
- 数量UI（個数 / 割合 / 固定ボタン）ごとの操作のしやすさ

**検証B（名寄せ）**

- 正解率
- **誤統合率**（別物を同じ品目にしてしまう割合。在庫が静かに狂うため最重要）
- 食材以外の除外精度
- 確認UIに回る行数（目安は1枚あたり数行以内）
- 2周目での別名テーブルのヒット率

## 8. 未解決事項・懸念点

### 決定待ち・要検証

1. **数量モデル**：個数 / パック / 割合のどれを正とするか。検証Aで操作性を比較して決める。調味料・米・油など数量管理しにくい品目の扱いも未定。
2. **品目の粒度**：「豚こま」と「豚バラ」を同じ「豚肉」にするかなど。粗くすると出庫は楽だが、型の指定（鶏肉のみ等）や提案の質に影響する。名寄せテストと型の設計の両方で確認が必要。
3. **「要補充」の判定基準**：在庫ゼロ以外の条件（定番品の最低在庫、購入頻度からの自動判定）が未定。
4. **賞味期限・消費期限の管理**：現状は仕様に含めていない。食品ロス削減や、期限が近い食材を優先する提案には必要になるため、扱いを決める必要がある。保管場所（冷蔵・冷凍・常温）の区別も未定。
5. **在庫のズレの補正**：ポチポチの押し忘れで実在庫とずれていく。棚卸しや手動修正の手段が必要。
6. **調理セッションの区切りと推定精度**：時間間隔での区切りでは、朝食と夕食、作り置きの同時調理などの境界が曖昧になる。出庫を忘れた食材や調味料は推定から抜ける。推定をMVP後に回す方針で問題ないか、最終確認が必要。
7. **提案の採用 = 作る、とみなす運用**：実際の買い物の流れに合うか未確認。

### 技術面

8. **GASの制約**：実行時間（1回6分）、UrlFetchの上限、同時アクセス時の競合（LockService）、履歴増加に伴うスプレッドシートの性能低下とアーカイブ方針。
9. **Claude API運用**：APIキー管理、コスト見積もり、障害時のフォールバック（AIが使えなくても入庫・出庫は成功させる）、JSON出力のプロンプト設計。
10. **PWA化**：GASのWebアプリはiframe配信のため、Service Workerやマニフェストの配置に制限があり、完全なPWA化は難しい可能性がある。オフライン時の挙動も未定義。
11. **別アプリのOCR連携**：OCR結果のテキストを受け渡す方法（手動貼り付け、共有機能など）が未定。

### 運用・その他

12. **利用者と権限**：個人利用か家族利用か。Googleアカウントによるアクセス制限と、同時操作の扱い。
13. **スーパーのゾーン定義**：登録方法（手入力かAI推定か）、複数店舗への対応、品目と売場ゾーンの紐付けルール。
14. **嗜好・アレルギー・食事制限**：嗜好データの蓄積方法（購入履歴からの推定か明示入力か）。アレルギーや食事制限は安全面から、旬レコメンドと献立提案の双方で考慮が必要。
15. **プライバシー**：レシート画像や購入履歴をClaude APIへ送信する点の方針。
16. **成功指標（KPI）**：継続率や出庫入力率など、ローフリクションが達成できたかの測り方。

### 入庫・保管場所まわり（追加）

17. **部門コードの汎用性**：サンプル1枚（1店）からの推測にとどまる。他のレシートで検証し、店ごとのコード表を自動学習にするか手入力にするかを決める。
18. **惣菜・味付け済み品の扱い**：ネギトロ太巻、ぶり照り焼きなどを管理対象にするか、確認UIで拾う運用にするかが未定。
19. **冷凍・常温の期限アラート**：冷凍は対象外とする案。常温の青果を対象にするかは未定。
20. **調味料・米・油など常温の定番品**：管理外にするか、補充リストのみで扱うかが未定。
21. **標準入数マスタ**：初期値の作り方と、ズレたときの補正のしやすさを検証する。
22. **レシート品名の途中切れと汎用すぎる品名**：「ミニずっしりデニッ」のように10文字前後で切れる行や、「鮮魚」のように中身が分からない行を名寄せで扱えるか。検証Bで確認する。
23. **行金額による検算**：行金額の合計に内税額を足すと合計に一致する店がある。読み取りミスの自動検知に使えるか検証する。
24. **検証Bのサンプル数**：週2回の買い物では集まるまで時間がかかる。まず10枚前後で一度評価し、過去のレシートが残っていれば併用する。
