# システム仕様書 v4：スマートライフスタイル管理システム

在庫管理の自動化と、買い物・献立の迷いの解消を目的とした家庭向けシステムの仕様書（改訂版）。v3以降に、手動入庫・在庫補正・売り場順・献立提案（型）・補充リストの除外と採用を実装した時点の内容を反映している。

- 改訂日：2026-10-30
- 状態の表記：【実装済】【未実装】【暫定】（実装したが検証や見直しが必要）【未決】
- 実装の詳細・運用手順は別紙「引継ぎ資料」を参照する。

## 1. システム概要・目的

### 目的

- 在庫管理の入力・運用負荷を極限までゼロに近づける。
- 名もなき家事（食材の管理・献立決め・買い物の迷い）をシステムとAIで軽くし、日々の生活の質を高める。
- 第一目標は「在庫管理を容易にすること」。使われなくなることが最大のリスクなので、すべての設計判断で入力の手軽さと応答性を優先する。

### コアコンセプト

「レシートで入庫 ➔ キッチン前でポチポチ出庫 ➔ 在庫から導く提案と最短ルートでお買い物」という、人間の物理的動線に一致したローフリクション・アーキテクチャ。

### v3からの主な変更点

- **手動入庫を実装した。** AIが使えないときも、レシートがない購入も、品目と数量を直接入れて登録できる（§3 ①、旧項目25の解消）。
- **在庫の補正を実装した。** 数えた現在数を入力すると、差分が「補正」としてログに残る（§3 ⑤、旧項目5の解消）。
- **売り場の管理を実装した。** 品目ごとに売り場（日本語名）を持ち、補充リストを売り場順に並べる。レシートの部門コードは、売り場を割り当てる補助として記録する（§3 ③）。
- **献立提案の第1段階を実装した。** 「型」による成立済み・あと一歩の判定、型のAI生成、一言からの型の追加、型の採用（§3 ④）。
- **補充リストの判定を変更した。** 最低在庫が空欄の品目は自動では載せない。品目ごとの除外と、採用した型の不足材料の表示を加えた（§3 ③）。
- **検証の方針を決めた。** 出庫の残りの検証は行わない。Geminiの名寄せ精度は、誤認識が複数回出た時点で測る（§7）。

## 2. 設計方針

1. **食材ベースを土台にする**：在庫と出庫は食材単位で扱い、レシピや料理名の入力を人間に求めない。
2. **レシピは使い捨ての仮説**：献立は確定した予定ではなく提案であり、採用しなくても何も起きない。
3. **人間に聞かず、システムが推定する**：名寄せなどは、まず別名テーブルとAIで推定し、確信度が低いものだけ確認する。
4. **粗い粒度から始める**：品目は「豚肉」「鶏肉」「葉物野菜」など粗めに設定し、必要になった時点で細分化する。
5. **失敗しても在庫操作は成功させる**：AI呼び出しの失敗が、入庫・出庫の操作を妨げない。
   - 出庫：AIを使わないため、この方針を満たしている【実装済】。
   - 入庫：AIが全モデルで失敗しても、手動入庫で登録できる。読み取りに失敗すると、手動入庫の欄が自動で開く【実装済】。
6. **手間を増やす運用は避ける**：例外の処理（売り場の割り当て、常備品の指定など）は、何もしなくても大きく困らない既定値を用意し、困ったときだけシートで直せる形にする。

## 3. コア機能要件

### ① 入庫管理【実装済】

#### レシート入庫の流れ

1. 入庫画面で「レシートを撮影する」を押し、写真を撮る（端末のカメラが起動する）。
2. 端末側で写真を長辺2200pxのJPEGに縮小し、サーバー（GAS）経由でGeminiへ送る。
3. Geminiが、店名・購入日・合計金額と、品目行ごとの情報（品名の原文、部門コード、購入数、行金額、品目、新規品目の保管場所と売り場、確信度）をJSONで返す。
4. サーバーが、別名テーブルとの完全一致を優先して品目を確定し、確認画面用のデータを返す。
5. 利用者が確認画面で必要な行だけ直し、「登録する」を押す。
6. 入庫ログ・別名テーブル・品目マスタ・部門コードの記録を更新し、補充の除外を解除する。

- 取得する情報は、品名、購入数、購入日の3つが基本。重量は取得しない。購入数は「2コ×単258」のような表記から読み取り、表記がなければ1とする。
- 食材以外（日用品・袋代・値引き行・お菓子・飲料など）は「対象外」として在庫に入れない。
- テキスト貼り付けによる入庫は実装していない【未実装】。

#### 手動入庫【実装済】

- 入庫画面の下部の折りたたみ「手動で入庫する」から、品目（保管場所ごとのプルダウン）と数量（0.5刻み）を選んで登録する。複数行をまとめて登録できる。
- 品目に「＋新規品目」を選ぶと、品目名・保管場所・売り場を入力して、品目マスタへ追加できる。
- レシートの読み取りに失敗すると、この欄が自動で開く。
- レシート入庫と同じ登録処理（`commitReceipt`）を使う。レシートの表記がないので、別名テーブルには学習しない。入庫日時は登録時刻。
- 通信に失敗して押し直しても、登録IDが同じなので二重登録にならない。内容を変えて押し直すと、新しい登録として扱う。

#### 名寄せ（表記揺れ対応）の構成

1. **別名テーブルで完全一致**：全角半角・ひらがなカタカナ・記号・空白を正規化したうえで、レシート表記（「ﾌﾞﾀｺﾏ」「豚小間切」など）を品目へ引く。ヒットした行は確信度1として扱い、AIの判定より優先する。
2. **未ヒット行はGeminiが判定**：品目マスタの一覧と一緒に画像を渡し、「どの品目か / 新規か / 対象外か」と確信度をJSONで返させる。マスタにない名前を返した場合は「新規」として扱う。
3. **確認UIに回す条件**：確信度が0.8未満の行、または新規品目の行。全件確認はしない。
4. **確定結果を別名テーブルへ自動追記**：利用者が確認した最終結果を学習する。既存の別名と違う品目に直した場合は上書きする。

> **注意**：検証Bはv2の構成（Claude `claude-haiku-5-5`、テキスト入力）で実施した。本番のGemini＋写真入力では名寄せの精度を測っていない【未検証・保留】。§7・§8 項目26を参照。

#### 確認画面【実装済】

| 区分 | 対象 | 初期状態 |
| --- | --- | --- |
| 確認が必要 | 確信度0.8未満、または新規品目の行 | 開いている |
| そのまま登録 | 確信度が高く、管理対象と判定した行 | 折りたたみ |
| 管理外と判断 | 確信度が高く、対象外と判定した行 | 折りたたみ。違うものだけ品目を選び直す。放置すれば管理外のまま確定する |

- 各行で、品目の選択（既存品目 / 新規品目 / 管理外）と数量を変更できる。新規品目のときは品目名と保管場所を入力する。売り場は、確認画面では選ばない。部門コードの割り当てまたはAIの推定で自動的に入り、誤りは品目マスタの売り場列で直す（影響は補充リストの並びのみ）。
- 管理外側を折りたたみで確認する理由：管理対象を誤って管理外にすると、気づかないまま在庫が欠ける。逆の誤りは余分なカードが出るだけで、本人が0にして消せる。
- 参考表示として、読み取った行金額の合計と、レシートの合計金額を並べる。自動での検算判定は行っていない（§8 項目23）。

#### 管理対象の基準と保管場所（決定・【実装済】）

管理対象は「冷蔵庫に入るもの」ではなく、**調理に使う生鮮食材全般**とする。品目マスタの「区分」で次の扱いにする。

| 区分 | 対象の例 | 出庫UIでの扱い | 期限アラート |
| --- | --- | --- | --- |
| 冷蔵 | 肉、魚、乳製品、葉物野菜、納豆 | 主画面（初期表示のタブ） | 未実装 |
| 冷凍 | 冷凍食品、冷凍肉 | タブで切り替え | 対象外（案） |
| 常温 | 玉ねぎ、じゃがいも、バナナ | タブで切り替え | 未定 |
| 管理外 | お菓子、飲料、日用品 | 表示しない（在庫に入れない） | なし |

- 新規品目の保管場所は、Geminiの推定または利用者の選択で決め、品目マスタに書き込む。
- 区分の判定順は、別名テーブル、Gemini。確定した区分は品目マスタに保存される。

#### 入庫時の数量の扱い【暫定】

- 数量は**個数（購入数）をそのまま在庫に加算**する。1パックを100%とする割合モデルと、標準入数マスタ（例：玉ねぎ1袋＝3個）は実装していない【未実装】。
- 品目は汎用名で登録する（例：牛豚合挽肉は「挽肉」）。

### ② 出庫管理（動的UIによるポチポチ減算）【実装済】

- **動的UI**：在庫が0より大きい食材のカードだけを、選択中の保管場所（冷蔵 / 冷凍 / 常温）のタブに表示する。残量が0になったカードは自動で消える。
- **ワンタップ減算**：「−1」「−½」「全部」の3ボタン。料理名の入力は不要。在庫を超えて減らない。
- **数量UI**：固定ボタン方式を採用【暫定】。ボタン定義は1か所（`ACTIONS`）で、割合UIなどに差し替えられる。
- **取り消し（Undo）**：直前の操作を1タップで取り消せる。取り消し履歴は端末のメモリ上にあり、画面を再読み込みするか、在庫を補正すると消える。
- **再読込**：サーバーの在庫で画面を合わせ直す。未送信の操作があるときは、送信後に行うよう案内する。
- **数量のタップ**：カードの数量をタップすると、補正タブでその品目の入力欄が開く（§3 ⑤）。

#### 応答性の方式（検証Aで採用を決定）

| 項目 | 方針 |
| --- | --- |
| 画面反映 | タップ時点で画面上の数量を即時更新する（楽観的UI更新） |
| 初回表示 | 在庫データをHTMLに埋め込み、起動後の読み込み往復をなくす |
| 書き込み | タップをキューに溜め、最初のタップから約1.2秒後にまとめて送信する |
| 保存形式 | セルの上書きではなく、1操作1行の追記型ログ |
| 失敗時 | 未送信キューを端末のlocalStorageに保持し、待ち時間を延ばしながら自動リトライ（最大30秒間隔）。再読み込み後も送信を再開する |
| 二重送信 | 操作ごとのopIdで、サーバー側が重複を無視する |

目標値：タップから画面反映まで100ms未満、起動から初回表示まで2〜3秒以内。検証Aの結果は「実用上問題ない」と判断した（§7）。

### ③ 自動補充リストと買い物ナビ【実装済】

補充リストには、次の2種類が載る。

1. **常備品の不足**：品目マスタの「最低在庫」に数字（0を含む）が入っている品目で、在庫がその数以下のもの。
   - **最低在庫が空欄の品目は、自動では載せない**。レシートから新規登録された品目は空欄で作られるので、常備にしたい品目だけ数字を入れる。
2. **採用した型の不足材料**：献立タブで「これにする」を押した型について、必須で足りない材料。選択肢のある材料は「豚肉か鶏肉か挽肉」のように1行にまとめる。型ごとに別の行で表示し、型名を添える。型が成立（不足がなくなる）すると、採用は自動で外れる。

#### 並び順

- **売り場順**：売り場順シートの順で並べる。同じ売り場の中は、保管場所、名前の順。売り場が未設定の品目は、最後の「売り場未設定」にまとまる。
- 採用した型の不足材料は、候補のうち売り場が分かる品目（品目マスタにあり、売り場が設定済み）の売り場に入る。分かる品目がなければ「売り場未設定」に入る。

#### 売り場の持ち方【実装済】

- 品目ごとの売り場は**日本語名**（「精肉」「野菜・果物」など）で品目マスタに持つ。並び順は売り場順シートで決める（仮の並びは、野菜・果物、精肉、鮮魚、卵・乳製品、豆腐・納豆、冷凍食品、調味料・乾物、その他）。
- **部門コードは、売り場を自動で割り当てる補助**として使う。レシートに書かれた部門コード（例：000604）を、登録のたびに部門コードシートへ自動で記録する（コード、件数、品目例、店名）。利用者は、見当がついたコードの「売り場」列だけを埋める。
- 新規品目の売り場の決まり方（優先順）：① 部門コードに割り当て済みの売り場、② Geminiの推定（売り場リストから選ぶ）、③ 未設定。売り場が空の既存品目も、割り当て済みのコードで登録されれば埋まる。入力済みの売り場は上書きしない。
- 将来コード中心の管理に寄せるときは、部門コードシートの割り当てを埋めるだけでよく、品目側の持ち方は変わらない。

#### 除外【実装済】

- 補充リストの常備品の行に「除外」ボタンがある。押すとリストから消え、下の「除外中（n）」の折りたたみに移る。「戻す」で復帰できる。
- **入庫すると、除外は自動で外れる**（レシート入庫・手動入庫とも）。在庫の補正では外れない。補正は数え直しであり、買ったわけではないため。
- 除外の記録は補充除外シートに保存し、再読み込みしても消えない。
- 行をタップすると取り消し線（買った印）が付く。この印は端末のメモリ上のみで保持する（§8 項目30）。

#### 未実装

- **旬のレコメンド**【未実装】：季節（月）と嗜好を踏まえ、「今週の旬の食材」を1〜2個だけ混ぜる。
- **最短経路の計算**は行わない。売り場順の並べ替えとして扱う。

### ④ 献立提案【第1段階を実装済】

#### 型（テンプレート）モデル【実装済】

レシピ（分量・手順）は持たず、「何が揃えば成立するか」だけを定義する。

- 型 = **必須ベース + 選択ベース + 自由枠**。
- 型シートの列：型 / 必須 / 選択 / 有効 / 備考。
- 材料は「、」で区切る。「豚肉|鶏肉|挽肉」のように「|」でつないだものは、**どれか1つあればよい**を表す。肉の種類を問わない型は「豚肉|鶏肉|挽肉」、鶏肉のみの型は「鶏肉」と書く。
- 有効の列が空の型、必須が空の型は使わない。
- 材料名は、品目マスタの表記と同じにする。正規化（全角半角・ひらがなカタカナ・記号）したうえで一致を見る。マスタにない材料は、買って入庫して品目に入るまで、足りないものとして扱う。
- 例：カレー = 必須（カレールー、豚肉|鶏肉|挽肉、玉ねぎ、にんじん、じゃがいも）／選択（なす、きのこ、トマト）。

#### 提案の出し方【実装済】

献立タブを開くたびに、今の在庫から次の2つを表示する（AIは使わない。在庫から機械的に判定する）。

1. **いま作れる**：必須の全要素について、在庫が1以上の品目がある型。足せる選択材料（在庫にあるもの）が多い型を優先する。
2. **あと一歩**：必須の不足が2個以下で、揃っている数が不足数以上の型。不足が少ない順。各カードに「これにする」ボタンがある。

- 各リストは3個ずつ表示し、「別の案」で次の3個に切り替える（一周する）。
- **選択ベースの解釈**：成立の判定には使わない。在庫にあるものを「足せる」候補として最大3個まで表示する【暫定・要確認】。
- **採用**：「あと一歩」の型で「これにする」を押すと、その型の不足材料が補充リストに入る。採用の記録は採用シートに保存し、型が成立すると自動で外れる。「取り下げ」で外せる。
- 採用していない型の不足は、補充リストに入らない。

#### 型の作成【実装済】

- **初期セット**：メニュー「在庫管理 → 型を生成（AI）」で、Geminiが家庭の定番の型を20個ほど生成し、型シートに追記する。有効の列には○が入る。要らないものは○を消す（取捨選択）。登録済みの型と同名のものは追加しない。
- **一言からの追加**：献立タブの「型を追加する」に、「麻婆なす」のような料理名を入力する。AIが下書き（型の名前・必須・選択）を作り、画面で確認・修正して登録する。同名の型があれば上書きを表示する。品目マスタにない材料も表示する（登録は止めない）。
- 型の生成ルールは共通の定数（`TYPE_RULES`）で持つ。

#### 自由枠【未実装】

- 型ごとに、在庫から足せる食材を2〜3個、AIが判定する。余りものや旬の食材を優先する。
- 現状は、選択の列に書かれた材料のうち、在庫にあるものだけを「足せる」として表示している。

#### 作った料理の推定【未実装】

- 出庫時に料理名は入力しない。
- 同じ時間帯（例：1〜2時間以内）の出庫を1つの「調理セッション」とみなし、材料の組み合わせからAIが型を推定する。どの型にも当てはまらなければ「不明」のままにする。
- 補助情報として、提案の採用履歴と、低確信度のときだけ表示する任意のワンタップ確認（「今日はカレーでしたか？」）を使う。
- 推定は夜間バッチ、または提案画面を開いた時に実行し、出庫の応答性に影響させない。
- 推定結果は履歴の参考情報であり、確定情報ではない。主な用途は、同じ型が続くのを避けることである。
- 出庫ログに日時と品目が残っているため、この機能は後から追加できる。

### ⑤ 在庫の補正（棚卸し）【実装済】

- ヘッダーの「補正」タブに、全品目が保管場所ごとに並ぶ。入力欄には現在数が入っている。数えた数に書き換えると、その行が強調され、ボタンに件数が出る。変えた品目だけが補正される。
- 出庫画面のカードの**数量をタップ**すると、補正タブに移り、その品目の入力欄が選択された状態になる。在庫0の品目も補正タブに出る。
- **補正は、差分をログに1行追記する**。種別は「補正」。差分は、サーバー側で、ログの生の合計（下限0を掛ける前）から求める。生の合計がマイナスになっている品目でも、入力した数に正しく合う。
- 再送しても二重に補正されない（2回目は差分が0になる）。
- 未送信の出庫があるときは補正を登録できない（出庫が補正値に上書きされないようにするため）。
- 補正に成功すると、出庫画面の取り消し履歴を消す。
- 補正は、補充の除外を解除しない。

## 4. システムアーキテクチャ・技術スタック

```
[ フロントエンド ] ──(HTTP)──> [ バックエンド ] ──(API)──> [ AIエンジン ]
 スマホ / タブレット          Google Apps Script (GAS)      Gemini API
 (出庫・入庫・補充・補正・献立の5画面)  (集計・名寄せ・判定・ログ追記)  (レシート読み取り・名寄せ・型の生成)
                                   │
                                   └──> [ データベース ]
                                        Googleスプレッドシート
```

- **バックエンド**：Google Apps Script（スプレッドシートに紐づくスクリプト）。サーバーレスでランニングコストがほぼゼロ。
- **データベース**：Googleスプレッドシート（§5 のシート群）。
- **AIエンジン**：Gemini API（`generativelanguage.googleapis.com`、`generateContent`）。
  - 基準モデルは `gemini-3.5-flash`。
  - 次の順に試す：`gemini-3.5-flash` → `gemini-3.6-flash` → `gemini-3.5-flash-lite` → `gemini-3.1-flash-lite`。
  - 200以外のときの動き：429・5xx・通信エラーは同じモデルを1.5秒待って1回再試行し、駄目なら次のモデルへ。404・400・403は使えないモデルとみなして次へ。401はキー不正として即エラー。応答がJSONとして読めない場合も次のモデルへ。
  - 出力は `responseMimeType: application/json`、`temperature: 0`。
  - 現在の用途：レシートの読み取りと名寄せ、型の生成、一言からの型の追加。
  - 将来の用途：旬の食材選定、自由枠の判定、調理セッションからの型推定。
- **フロントエンド**：GASの`doGet()`でデプロイするウェブアプリ（HTML / JavaScript / CSS、1ファイル）。PWA化は未検討【未決】。
- **提案の判定**：成立済み・あと一歩の判定は、サーバー（`getSuggestions`）と画面（採用した型の不足の算出）の両方に同じ規則で実装している。規則を変えるときは、両方を直す（§8 項目34）。

## 5. データ設計

- **追記型ログを正とする**：入庫・出庫・補正を1操作1行で追記し、在庫は集計（品目ごとの増減の合計、下限0）で求める。競合に強く、Undoは逆符号の行の追記で実現する。

### シート定義【実装済】

| シート | 列 | 備考 |
| --- | --- | --- |
| 品目マスタ | 品目 / 区分（冷蔵・冷凍・常温・管理外） / 最低在庫 / 売り場 | 新規品目は入庫確定時に追記される。**最低在庫は空**（常備品にするまで補充に載らない）。売り場は自動割り当てまたは空 |

| ログ | 日時 / 品目 / 増減 / opId / 端末 / 種別（入庫・出庫・補正） | 入庫の日時は購入日の12:00（日本時間）。購入日が不明なら登録時刻 |

| 部門コード | コード / 売り場 / 件数 / 品目例 / 店名 | レシートの部門コードの観測記録。売り場の列だけ人が埋める。コードは文字列（先頭の0を保つ）。店名は初出の記録のみで、照合には使わない |
| 型 | 型 / 必須 / 選択 / 有効 / 備考 | 材料は「、」区切り、「\|」は「どれか1つ」。有効が空の行は使わない |

## 6. データフロー・運用シナリオ

1. **【買う】** スーパーで買い物 ➔ 入庫画面でレシートを撮影 ➔ 低確信度・新規の行だけ確認して登録。読み取れないとき・レシートがないときは、手動入庫。
2. **【作る】** 冷蔵庫から食材を取り出す ➔ 出庫画面で使った分だけポチポチ。在庫は即時に画面へ反映され、書き込みは裏で行われる。
3. **【補う】** 買い物前にスマホを開く ➔ 補充画面で要補充アイテムを売り場順に確認。つくりたい献立があれば、献立画面で「あと一歩」の型を採用し、不足材料を補充リストに入れる。いらない品目は「除外」する。
4. **【整える】** 在庫が実際とずれたときは、補正画面で現在数を直す。

31. **日付と時刻**：購入日の時刻を日本時間の12:00に固定している。手動入庫と補正の時刻は登録時刻。
32. **モデル名の変更への追随**：Geminiのモデル名や提供状況は変わりうる。404が増えた場合は、切り替えリスト（`MODELS`）を最新に更新する。

### 追加（v4）

33. **最低在庫が空欄の運用**：新規品目は最低在庫が空で作られ、補充リストに載らない。常備にしたい品目だけ、手でシートに数字を入れる。すでに0が入っている品目は、これまでどおり常備品として載る。常備にしない品目は、セルを空にする。
34. **提案の判定が2か所にある**：成立済み・あと一歩の判定（サーバー）と、採用した型の不足の算出（画面）が、同じ規則を別々に実装している。材料名の正規化（`norm_`と画面側の`norm`）も同様。規則を変えるときは両方を直す。
35. **部門コードは店ごとに区別しない**：コードは店に関係なく共通として扱う。複数の店のレシートを入れると、同じコードが別の売り場を指して、割り当てを誤る可能性がある。誤っても影響は補充リストの並びのみ。
36. **売り場の誤り**：コードの割り当てを間違えると、そのコードで読まれた新規品目が誤った売り場に入る。品目マスタの売り場列を直せば済む。
37. **「選択」ベースの解釈**：成立の判定に使わず、「足せる」候補として表示している。「選択のうち1つ以上が必要」な型が出てきた場合は、型の書式の拡張が必要。
38. **型の材料名とマスタ表記の不一致**：型の材料名が品目マスタの表記と（正規化しても）異なると、在庫があっても成立しない。表記のズレに気づきにくい。型の生成・追加でマスタ表記に揃えるよう指示しているが、保証はない。
39. **型の生成・追加のGemini応答が未確認**：サーバー側の処理は、模擬の応答で検証した。実際のGeminiの応答での品質（必須の過不足、数）は確認していない。
40. **採用した型の不足は型ごとに別行**：複数の型を採用して、同じ材料が不足している場合は、重複して表示される。
41. **除外・採用は端末間でリアルタイム同期しない**：記録はシートに保存され、画面を開くときに読み込まれる。複数端末で同時に使う場合、他の端末の変更は再読み込みまで反映されない。
42. **補正の制約**：未送信の出庫があると登録できない。補正は、補充の除外を解除しない。
43. **自由枠・旬・調理セッションの推定は未実装**：§3 ③④を参照。
