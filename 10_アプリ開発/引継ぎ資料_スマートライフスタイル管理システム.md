## 2. 成果物

| ファイル | 役割 |
| --- | --- |
| `Code.gs` | バックエンド（GAS）。画面配信、在庫集計、ログ追記、Gemini呼び出し |
| `index.html` | フロントエンド。出庫・入庫・補充の3画面（HTML・CSS・JavaScriptを1ファイルに収めている） |

GASプロジェクトに置くファイルはこの2つだけ。HTMLファイルの名前は必ず小文字の `index`（コード内で `createTemplateFromFile('index')` と指定している）。検証用のコード（検証Aの `Code.gs`・`index.html`、検証Bの `Code_検証B.gs`）を同じプロジェクトに残すと、関数名が重なって誤動作するため、別のプロジェクトに分ける。

検証用コードの位置づけ：検証Aは出庫の方式比較、検証Bは名寄せの3方式比較（実レシートの行を貼り、`結果`・`集計`シートに指標を出す）。Geminiでの名寄せを再評価するときは、検証Bのコードの `askClaude_` をGemini呼び出しに差し替えるのが近道。

## 3. 環境構築とデプロイ

1. 新しいGoogleスプレッドシートを作り、「拡張機能 → Apps Script」を開く。
2. `Code.gs` と `index.html` の内容を貼る（HTMLは「ファイルを追加 → HTML」で `index` を作る）。
3. スプレッドシートを再読み込みし、メニュー「在庫管理 → 初期セットアップ」を実行する。`品目マスタ`（サンプル16品目）、`別名`、`ログ` の3シートができる。既存のシートは消さない。
4. Gemini APIキーを設定する。メニュー「Gemini APIキーを設定」か、「プロジェクトの設定 → スクリプト プロパティ」で `GEMINI_API_KEY` を追加する。
5. エディタで `testGemini` を実行し、実行ログに `OK: gemini-3.5-flash …` のように出ることを確認する（キーとモデルの切り分け）。初回はUrlFetchなどの権限承認が出る。
6. 「デプロイ → 新しいデプロイ → ウェブアプリ」で公開する。
7. 発行されたURLをスマホ・PCで開く。

**コードを直したあとは、必ず新しいバージョンで再デプロイする**（デプロイを管理 → 鉛筆アイコン → バージョン：新バージョン → デプロイ）。ウェブアプリのURLは、デプロイ時点のバージョンを配信する。

初期在庫の入れ方：入庫画面でレシートを登録するか、`ログ` シートに「日時 / 品目 / 増減 / opId（一意な文字列）/ 端末 / 入庫」の行を直接追加する。

## 4. データ構造

| シート | 列 |
| --- | --- |
| 品目マスタ | 品目 / 区分（冷蔵・冷凍・常温・管理外） / 最低在庫 |
| 別名 | 別名（レシート表記の原文） / 品目（「対象外」も可） / 店名 |
| ログ | 日時 / 品目 / 増減 / opId / 端末 / 種別（入庫・出庫） |

- 在庫 = ログの品目別の増減合計（下限0、小数第2位まで）。在庫専用のシートはない。
- 区分が「管理外」の品目は、在庫画面に出さない。
- 別名の照合は、正規化（全角半角・ひらがなカタカナ・記号・空白をならす）した文字列で行う。正規化の実装は `norm_`。
- ログの重複排除は、直近500行の範囲のopIdで行う（`DEDUPE_WINDOW`）。

## 5. コード構成

### Code.gs

| 関数 | 役割 |
| --- | --- |
| `onOpen` / `setup` / `setApiKey` | メニュー、初期シート作成、APIキー保存 |
| `doGet` | 画面を返す。在庫をJSONにしてHTMLへ埋め込む（初回表示の高速化） |
| `getStock` / `getStock_` | 在庫の集計。画面の再読込と初期表示で使う |
| `appendLogs` / `appendRows_` | 出庫のログ追記（ロック、opIdによる重複排除） |
| `parseReceipt` | 写真をGeminiで読み取り、別名テーブルを優先して確認画面用の行を返す |
| `commitReceipt` | 確認済みの行を入庫ログに追記し、別名・品目マスタを更新する |
| `callGemini_` | Geminiの呼び出し。リトライとモデルの切り替えを担当 |
| `testGemini` | エディタ実行用の疎通確認 |
| `readRows_` / `loadAlias_` / `norm_` | 補助関数 |

主な定数：`MODELS`（試すモデルの順序）、`CONF_TH`（確認に回す確信度のしきい値、0.8）、`ZONES`、`DEDUPE_WINDOW`。

`appendLogs`・`parseReceipt`・`commitReceipt` は、画面から引数付きで呼ばれる関数。エディタの「実行」で直接動かすと引数が空でエラーになる（その旨のエラーメッセージを出す処理を入れてある）。

### index.html

- 3つのセクション：出庫（`#vOut`）、入庫（`#vIn`）、補充（`#vShop`）。ヘッダーのタブで切り替える。
- 出庫：`ACTIONS`（数量ボタン定義）、`act`（楽観的更新とキュー追加）、`flush`（まとめて送信、失敗時は再試行）、`persist` / `restore`（未送信キューをlocalStorageに保存・復元）。
- 入庫：`shrink`（写真を長辺2200pxのJPEGに縮小）、`renderReview`（確認画面）、`commit`の処理（確認ボタン）。
- 補充：`renderShop`（在庫が最低在庫以下の品目を表示）。
- 先頭の別の `<script>` が、実行時エラーを画面上部のステータス欄に表示する。画面が動かないときの切り分けに使う。

## 6. 主要な設計判断とその理由

| 判断 | 理由 |
| --- | --- |
| 追記型ログを正とし、在庫は集計で求める | 競合に強い。Undoは逆符号の行の追記で済む。型推定に使う日時・品目も残る |
| 出庫は楽観的更新＋バッチ送信 | 検証Aで応答性が実用上問題ないと確認。連続タップでも画面が止まらない |
| 入庫の確認は低確信度・新規の行のみ | 全件確認は運用負荷が高く、使われなくなるリスクが最大 |
| 管理外の確認は折りたたみ（違うものだけ直す） | 管理対象を誤って管理外にすると、気づかないまま在庫が欠ける |
| 別名テーブルを優先し、AIの結果より先に採用 | 命中すればAI呼び出しの誤りを避けられる。使うほど命中率が上がる |
| 写真をGeminiへ直接渡す（別アプリのOCRを使わない） | 手順が減る。読み取りと名寄せを1回の呼び出しで行える |
| Geminiのモデルを複数用意し、順に試す | 503（過負荷）や404（モデルの廃止・名称変更）でも入庫を止めないため |
| ログの`opId`を「レシートID-行番号」にする | 通信失敗後に「登録する」を押し直しても二重登録にならない |

## 7. 既知の制限・リスク

優先して対応を検討するものから順に並べる。詳細は仕様書 §8 の項目番号を参照。

1. **手動で入庫できない**（項目25）。Geminiが全モデルで失敗すると入庫できない。設計方針5（AIの失敗が操作を妨げない）を満たしていない。
2. **Geminiでの名寄せ精度が未測定**（項目26）。検証Bで確認したのはClaude・テキスト入力の構成。
3. **在庫補正の手段がない**（項目5）。押し忘れで実在庫とずれると、`ログ` シートを手で編集するしかない。
4. **別名の誤学習が固定される**（項目29）。確認に回らなかった誤りが別名に登録される。修正は `別名` シートを手で編集する。
5. **ログ肥大化による性能低下**（項目27）。表示のたびにログ全体を集計している。
6. **プライバシー**（項目15）。レシート画像をGemini APIへ送信している。無料枠・有料枠のデータの扱いを確認する。
7. 取り消し履歴と補充リストの「買った」印は、再読み込みで消える（項目30）。
8. 検証A・Bの数値が未記録。

## 8. トラブルシューティング

| 症状 | 原因と対処 |
| --- | --- |
| エディタから `commitReceipt`・`parseReceipt`・`appendLogs` を実行するとエラー | 画面から引数付きで呼ぶ関数のため、エディタの実行ボタンでは動かない。画面（ウェブアプリのURL）から操作する |
| 画面にタブとボタンだけが出て、カードや「同期済み」が出ない | スクリプトが実行されていない。デプロイ済みの `index.html` が最新か確認し、新バージョンで再デプロイする。ステータス欄にエラー文が出ていればそれを確認する |
| コードを直したのに反映されない | 再デプロイしていない。デプロイを管理 → 新バージョンでデプロイ |
| 画面に関数名（`setApiKey` など）が出る | `index.html` に `Code.gs` の内容が混ざっている。両ファイルの中身を確認し貼り直す。HTMLのファイル名は小文字の `index` |
| 読み取りで「すべてのモデルで失敗しました → …」 | 各モデルの失敗コードが並ぶ。`400`＋「API key not valid」→キーの誤り。`404`が並ぶ→モデル名が現行にない。`503`・`429`が並ぶ→混雑のため時間をおく |
| `testGemini` が失敗する | 同上。まずAPIキー（`GEMINI_API_KEY`）とモデル名（`MODELS`）を確認する |
| 在庫が増減しない、重複する | `ログ` シートのopIdを確認。同じopIdの行は追記されない設計 |
| 初回の画面表示が遅い | ログ件数が増えている可能性（項目27） |

## 9. 次にやること（推奨順）

1. **実レシートでの精度評価**：Gemini・写真入力で、検証Bと同じ指標（正解率、誤統合、確認なしで確定した誤り、除外精度、確認UIに回る行数）を測る。数値を仕様書 §7 に記録する。
2. **手動入庫の画面**：品目と数量を直接入れて登録する。AI障害時の代替になり、レシートがない購入にも使える。
3. **在庫の手動補正**：品目ごとに現在数を直す操作（補正の行をログに追記する）。
4. **出庫の検証の残り**：高速連打、複数端末、機内モードでのデータ欠損の確認。
5. **ログの集計方針**：件数が数千行になる前に、繰越行の導入などを決める。
6. **プライバシー方針の決定**（項目15）。
7. 後続機能：旬のレコメンド → ゾーン順の並べ替え → 型による献立提案 → 調理セッションの型推定。
