### Q1. wrangler.jsonc には何が書かれてる?

- Cloudflare Workers のデプロイ設定ファイル
- 名前、エントリポイント(Astro の SSR)、静的アセット(`./dist`)、オブザーバビリティ
- D1 データベースのバインディング(`DB`)
- Cloudflare Access 用の環境変数(`ACCESS_TEAM_DOMAIN`、`ACCESS_AUD`)
- 「Access で保護した Astro SSR アプリが D1 を使う構成」だとわかる

### Q2. compatibility はどういう意味?

- `compatibility_date`: 「この日付時点のランタイムの挙動で動かす」固定指定。Cloudflare 側の更新で既存コードが壊れるのを防ぐ
- `compatibility_flags`: 個別機能のオン・オフ。`global_fetch_strictly_public` は非公開宛先への `fetch` を禁止(SSRF対策)

### Q3. SSR で動かすとき、ローカルのファイルはどう読む?

- Workers にはファイルシステムが無く、`fs` で実行時に読めない
- 代替手段: `import` / `?raw` / `import.meta.glob`(ビルド時に埋め込む)、コンテンツコレクション、`public/` + `ASSETS`、動的なものは R2 / D1 / KV
- ローカル開発では `fs` が動いても、本番では動かない場合がある

### Q4. このフォルダ構成を説明して

- `src/`(本体)、`public/`(静的ファイル)、`dist/`(ビルド出力)、`migrations/`(D1 の構造変更履歴)、`seed/`(初期データ)
- 自動生成物: `.astro/`、`.wrangler/`、`node_modules/`、`dist/`
- 設定系: `wrangler.jsonc`、`astro.config.mjs`、`package.json`、`tsconfig.json`、`worker-configuration.d.ts`(型定義)

### Q5. 依存パッケージのバージョン固定は、コンテナと似てる?

- 目的は似ている(環境の再現)が、固定する範囲が違う
- `package-lock.json` は npm パッケージだけ。コンテナは OS・ランタイム・アプリ一式
- このプロジェクトでは、ランタイムの固定にあたるのが `compatibility_date`

### Q6. ランタイムがしっくり来ない

- ランタイム = コードを読んで実行する実行環境(楽譜と演奏者のたとえ)
- Node.js、ブラウザ、Workers で使える機能が違う(`fs`、`document` など)
- Workers では Cloudflare がランタイムを提供・管理する

### Q7. 実行環境 = サーバーと JS 実行プログラムをひっくるめたもの?

- ほぼ正しい。ただし「JS をインストール」ではなく「JS を実行するプログラムをインストール」
- 広い意味(ハード・OS・ランタイム・ライブラリ全体)と狭い意味(ランタイム本体)がある
- Workers では下の層を全部 Cloudflare が用意する(サーバーレス)

### Q8. Cloudflare がランタイムを提供してくれるなら使い、無ければ GCP などで丸ごと準備?

- 二択ではなく段階がある: コードだけ渡す(Workers / Lambda) → コンテナを渡す(Cloud Run など) → VM を借りる(EC2 など)
- Workers は軽く手軽だが、ファイルシステムが無いなどの制約がある
- このプロジェクトの規模なら今の構成で問題なし

### Q9. Workers・D1・R2 のような点が使いやすい。AWS や Google に似たものは?

- 対応表: Workers ≒ Lambda / Cloud Run、D1 ≒ Aurora / Cloud SQL、R2 ≒ S3 / Cloud Storage、KV ≒ DynamoDB / Firestore など
- Cloudflare の強みは、バインディングによる手軽さ、無料枠、R2 の転送料無料
- AWS / GCP は選択肢が多く、複雑な要件向き

### Q10. 編集・commit・push・ビルド・デプロイの関係

- Git(commit / push)は「コードの履歴と共有」、ビルド・デプロイは「本番への公開」で別系統
- commit と push も別(push するまで GitHub に届かない)
- 手動デプロイと、GitHub 連携による自動デプロイの2パターン
- D1 のマイグレーションは、デプロイとは別に手動で適用が必要

### Q11. GitHub と Cloudflare は連携してる

- 対象ブランチに push → Cloudflare 側がビルド・デプロイする自動化の構成
- ビルドは Cloudflare 上で走るので、必要なファイルが Git に入っていること、Node.js のバージョンなどに注意
- 失敗はダッシュボードのビルドログで確認、戻したいときはロールバック

### Q12. `npm run build` / `dev` / `deploy` があった気がする

- `package.json` の `scripts` に定義されたコマンド
- 実物を確認: `dev` = `astro dev`、`build` = `astro build`、`deploy` = `astro build && wrangler deploy`
- `deploy` にマイグレーションは含まれていない。`generate-types` と `cf-typegen` は重複

### Q13. 設定ページで入力したデータは、どこに行く?

- 本番は Cloudflare 上の D1、ローカルは `.wrangler/` 内の SQLite。この2つは別物
- コードをデプロイしてもデータは送られず、Git にも入らない
- 確認方法: ダッシュボード、または `wrangler d1 execute`(`--remote` が本番)

### Q14. 本番データがクラウド上だけだが、重要なDBはどうする?

- クラウドはハード故障には強いが、操作ミス・バグ・誤削除は複製されるので守れない
- 対策: 自動バックアップと復元機能、別の場所への定期バックアップ(3-2-1ルール)、復元の練習、本番へのアクセス制限
- 趣味サイトなら、時々 `wrangler d1 export` で書き出す程度でも効果が大きい

### Q15. `SELECT * FROM テーブル名` のテーブル名には何を入れる?

- 自分のDBに実在するテーブル名
- 調べ方: `SELECT name FROM sqlite_master WHERE type='table'`、`migrations/` の `CREATE TABLE`、ダッシュボード
- `--remote` の有無で、本番かローカルかが変わる

### Q16. SQL クエリとは?

- データベースへの命令文。基本は `SELECT`(読む)、`INSERT`(追加)、`UPDATE`(変更)、`DELETE`(削除)
- `WHERE` を付け忘れると全行が対象になる。本番では先に `SELECT` で確認する

### Q17. SQL が書ける人 = 作成済みDBから取り出せる人?

- 取り出しは中心スキルだが、範囲はそれだけではない
- 書き換え、構造の作成・変更(`CREATE TABLE`、`ALTER TABLE`)も SQL の範囲
- 入門 → 実務(`JOIN`、集計) → 設計・性能改善、と幅がある

### Q18. DB設計も SQL の範囲なら、開発で重要なポジション?

- その通り。コードは直しやすいが、データ構造は本番データがあるので直しにくい土台
- 小規模では1人が全部担当し、大規模では分業する
- 将来を考えすぎず、素直に設計して、マイグレーションで少しずつ変える

### Q19. (migrations の SQL 3本を提出)設計を見てほしい

- 5テーブル: `events`、`event_sources`、`songs`、`streams`、`setlist_entries`
- `setlist_entries` が配信と曲の多対多を結ぶ中間テーブル
- 日付の不確かさの表現、SQLite に沿った型選び、使い道のあるインデックスなど、素直で良い設計
- 改善候補: 削除時の扱い、`CHECK` 制約、`position` の重複防止

### Q20. 中間テーブルが必要になるのはどんな時?

- 多対多(両方向に複数)のとき。1つのセルに複数の値は入れられない
- 結びつき自体の情報(順番、開始秒数など)も置ける
- 見分け方は「逆から見ても複数あるか?」

### Q21. 多対多で中間テーブルが2個以上になることはある?

- 多対多の関係の数だけ増える。特別なことではない
- パターン: 3つ以上のテーブルの連鎖、同じ2テーブル間で意味の違う関係(いいねとブックマークなど)、中間テーブルが別テーブルから参照される場合

### Q22. 授業の履修の例を詳しく

- `students`、`classes`、中間の `enrollments`、そこにぶら下がる `grades`
- 1つの履修に複数の成績が付くので、履修が独立した実体として `id` を持つ
- `grades` が `enrollment_id` を持つ設計は、履修していない授業の成績が入らず、整合性を保ちやすい

### Q23. 複雑になったら、王道の設計手法は?

- ER図を描き、概念 → 論理 → 物理の順に設計する
- 名詞は実体、動詞は関係の候補。正規化でデータの重複・矛盾を防ぐ
- 道具: draw.io、dbdiagram.io、Mermaid など。実際に使うクエリを想像して設計の抜けを探す

### Q24. Mermaid で ER 図を書いて

- 5テーブルとその関係を Mermaid の `erDiagram` で出力
- 記号(`||--o{` = 1対多)の読み方、GitHub や mermaid.live での表示方法を説明
- `events` 系と `setlist` 系は、現状では独立した2グループ

### Q25. AIに丸投げで作ったが、ちゃんと考えると難しいことをやっていた?

- 難しいというより、定番の型に素直に当てはめてくれていた
- ただし任せきりだと、困ったときに自分で直しにくい
- 設計の勘所を知っていれば、AI の出力を「読んで判断する」側に回れる

### Q26. 削除時に子のデータが残る(`ON DELETE CASCADE` が無い)を詳しく

- 補正: D1 では、残るのではなく**削除が拒否されてエラー**になるのが正確
- 選択肢: `NO ACTION` / `RESTRICT` / `CASCADE` / `SET NULL`
- 付属物なら `CASCADE`、守りたい履歴なら `RESTRICT` と、関係ごとに決める
- 既存テーブルへの後付けは作り直しが必要。削除は `db.batch` でまとめると安全

### Q27. しっかりコードレビューするには、親子関係とER図を出させて実用に合うか確認すればOK?

- DB設計のレビューとしては良い出発点だが、コード全体には足りない
- 追加で見る点: SQL のパラメータ化、認証・権限、入力検証、エラー処理、マイグレーション、秘密情報
- AI を使うコツ: 実物から図を作らせる、理由を聞く、観点を絞る、別セッションで再レビューする
- 最終的に「自分の使い方に合っているか」を判断するのは人間

### 12:51 「違くて」の文法について
**要点**
- 違くてや違かったという表現は形容詞のように扱った誤用である。
- 違うの正しい形は違ってや違いましたである。
- 大きいや正しいなどの形容詞はくてをつけて大きくてや正しくてとなる。
- 違うは動詞に分類されるため形容詞とは活用ルールが異なる。

### 13:14 心理的距離の概要
**要点**
- 心理的距離とは主観的な距離感であり物理的距離とは異なる。
- 心理的距離は親密さや共感の度合いに基づき変動する。
- 仕事との心理的距離は仕事に対する主観的な距離感を表す。
- 距離が近すぎるとストレスを溜めやすく遠すぎるとモチベーションが低下する。
- 適切な距離を保つことで成果と健康を維持しやすくなる。
